# 业财法审批流（V4.0，P01–P07）

店主 2026-11-26 交来《业财法审批流开发批次拆分与执行说明-从零梳理版》（以下简称「执行说明」）、42 项任务清单和功能结构图，要求通读后按批次开发，中途不停。执行说明依据的《汤崎审批流程_需求设计 PR 包 V4.0》（PR.md、`docs/00_统一流程底稿.md`、`docs/08_验收案例.md` 共 48 个场景）没有一起给到，仓库里也找不到。所以这里以执行说明和任务清单为准。验收场景只按编号和清单里的规则来理解，等拿到原包再逐条对照（见 `PENDING_DECISIONS.md` 的 AV01）。

服务对象：宝安汤崎、池里、PAJAMA、新生乐园。目标是建一套共用的业财法审批底座：正常事项走得快，重大风险有人负责，供应商、SKU、合同、付款、备用金、人力付款全链路可以追溯。

## 1. 和现有审批中心的关系

现有的「审批中心」（`docs/APPROVALS.md`，迁移 073/076，`modules/approvals`）只服务采购单、物资单据、付款、报销、合同、付款申请这些已有单据。它的约束是：
- 审批链最多 3 级；
- 岗位组只有负责人、财务、店总、店主、法务；
- 店主算在每一组里。

执行说明要求「全部按从未开发处理」：
- 4 级以上的链路；
- CFO、经营主体负责人、董事长等角色映射，且不能拿店主顶替；
- 会签；
- 知会；
- 回避；
- 履约执行人和内控节点。

两者差异太大。所以新建「业财法」模块（表前缀 `gf_`，代码在 `modules/govflow`、`shared/govflow.ts`），共用登录、员工、部门、经营主体（`legal_entities`）、站内通知和审计，不改动现有审批中心的行为。

## 3. P01 审批引擎与角色底座（迁移 `400_govflow_core.sql`）

### 3.1 角色映射（P01-02）

角色共 13 个：
- 财务审核人、财总、CFO、法务；
- 经营主体负责人（CEO）、董事长、业态总经理；
- 供应链负责人、章证管理员、出纳；
- 内部履约执行人、内控、人力资源。

配置规则：
- 店主在「WCP → 业财法审批 → 角色映射」里把真实账号配进去，权限是 `gf.roles`，默认只给总裁。
- 一个角色可以配多个人，可以限定在某个经营主体。
- 撤销只记时间，不删记录。
- 店主不在任何角色里，也不自动顶替这些角色。
- 部门负责人取组织架构里的部门负责人（`departments.head_id`）。
- 全系统最高角色称「董事长」，不出现「集团总裁」。

### 3.2 审批链（P01-01、03、06、07）

节点有四种：
- 部门负责人；
- 内部履约执行人；
- 某个角色（其中任意一人同意即可）；
- 几个角色各由不同的人同意（`all`）。

`all` 同时覆盖两种用法：
- 「财总＋CFO 共同审批」：两人都同意才通过，任一人驳回就不通过。备用金超额特批、HR 付款、月度额度核定都复用这个节点（`COSIGN_FINANCE_CFO`）。
- 「财务、法务分别审核」：并行分审，分别出结论。

同一级里一个人只能占一席，数据库里有唯一索引兜底。链路最多 12 级。

每个节点标注性质：
- 审核；
- 终审（金额或风险终审）；
- 特批。

排链在提交时完成（纯函数 `planFlow`），结果存进这一轮审批：
- **履约执行人 +1**：合同类事项在部门负责人之后、财法之前插入履约执行人。履约执行人和部门负责人是同一人时不重复（场景 43）。
- **内控参与**：事项带了招标、单一来源、新供应商、核心品类、价格异常任一标记时，在终审前加一级内控。常规库内业务不加签（场景 47）。内控的周报和月度审核放在 P03 和 P06。
- **回避**：终审和特批节点里，提交人和「事项本人」（报销人、收款员工等）都不能审（场景 12）。
  - 角色里还有别人的，节点保留，由别人审。
  - 没有别人的，按 财务审核人 → 财总 → CFO → CEO → 董事长 往上移一级。会签节点上移时会避开节点里已有的角色。
  - 董事长本人的事项，如果没有另一位董事长，节点保留，并提示店主加一位授权人。
- 每一级在提交时都要确认现在有人能审，没人的不让提交（`GF_NO_APPROVER`），避免卡在半路。
- 部门负责人自己发起，或履约执行人本人发起的，那一级视同已确认，记一条「自动跳过」。

审批动作：
- **同意**：坐上一席。
- **退回**：发起人改了再提交，从第 1 级走新一轮。
- **驳回**：不通过，这个事项不能再提交，要重新发起。

退回和驳回都要写原因。每个动作都带操作编号，重提不会重复记。级别对不上时拒绝（`GF_MOVED`）。

### 3.3 通用事项的金额终审（P01 用来验证引擎）

审批金额一律按不含税口径。以下是 P01「通用事项」的终审档位，P04 的七类合同沿用同一档位：

| 金额 | 终审 |
| --- | --- |
| < 1 万 | 财总 |
| 1 万到 5 万（不含 5 万） | CFO |
| 5 万到 30 万（不含 30 万） | CFO 审，CEO 终审 |
| ≥ 30 万 | CEO 审，董事长终审 |

另外两条：
- 重大风险、预付款、超预算的，至少到 CFO。
- 30 万的合同类事项是 5 级：部门负责人 → 履约执行人 → 财法分审 → CEO → 董事长。

用例在整值前后一分钱（9,999.99 / 10,000.00、49,999.99 / 50,000.00、299,999.99 / 300,000.00）各验一遍。

### 3.4 知会（P01-04）

- 审批通过以后知会董事长、业态总经理、财总、CFO。
- 知会只是通知，不需要点同意。
- 同一事项同一人只知会一次。已在审批链里出过结论的人和发起人不再知会。
- 以下情况即时站内提醒：金额 ≥ 5 万、异常、紧急、重大风险、特批。
- 其余的进日报：每天 18 点以后，每分钟任务按人汇总成一条站内信，发过的不再发。

### 3.5 微信特批补登（P01-08）

1. 紧急事项两人微信确认以后，在系统里登记：
   - 必须是两个不同的确认人，登记人不能是确认人之一；
   - 生成唯一特批编号 `TP…`；
   - 可以关联原事项。
2. 补登期限是确认日起 1 个工作日（节假日表里的节假日不算，调休上班算）。
3. 补登时要上传需求说明和 OK 截图，各至少一份：
   - 只收 PNG、JPG、WEBP、PDF；
   - 每份不超过 5 MB；
   - 会核对文件头。
4. 补登只能做一次，不重复审批。
5. 关联的事项在补登前状态是「特批待补登」，不能「执行完成」。

### 3.6 通用流程状态（P01-09）

主流程：草稿 → 审核中 → 待执行 → 执行中 → 已完成 → 已归档。

另有：退回、驳回、撤回、特批待补登、后补待完成。

逾期是另一个标记：过了期限还没完成的算逾期。

状态不另建表，由纯函数 `deriveStatus` 从事项、最近一轮审批、特批这几张表算出来。

### 3.7 看得到谁

能看事项详情的人：
- 发起人、履约执行人、事项本人；
- 审批链里能审或审过的人；
- 知会对象；
- 关联特批的登记人和确认人；
- 店主、内控、董事长（这三类看得到「全部」）。

补登的文件也只给这些人下载。

### 3.8 页面

页面在「WCP → 业财法审批」（`/oa/gov`），分区如下：
- 待我审批；
- 我发起的；
- 知会我的；
- 全部；
- 微信特批；
- 角色映射。

事项详情在 `/oa/gov/:id`：
- 显示审批链每一级，会签和并行分审还等谁；
- 显示排链时的调整说明（同一人不重复、加内控、回避上移）；
- 可以同意、退回、驳回；
- 显示知会和特批；
- 可以开始执行、完成、归档。

手机和电脑用同一页面。

## 4. 接口（P01）

| 接口 | 用途 |
| --- | --- |
| `GET /api/gf/meta` | 角色、我的角色、经营主体、部门（含负责人）、员工 |
| `GET /api/gf/roles` | 角色映射列表 |
| `POST /api/gf/roles` | 加角色映射（`gf.roles`） |
| `POST /api/gf/roles/:id/revoke` | 撤销角色映射（`gf.roles`） |
| `GET /api/gf/docs?box=todo\|mine\|cc\|all` | 事项列表 |
| `POST /api/gf/docs` | 新建事项（操作编号幂等，默认同时提交） |
| `GET /api/gf/docs/:id` | 事项详情 |
| `POST /api/gf/docs/:id/submit` | 提交（带版本号） |
| `POST /api/gf/docs/:id/act` | 审批动作（带操作编号、级别） |
| `POST /api/gf/docs/:id/withdraw` | 撤回（带版本号） |
| `POST /api/gf/docs/:id/execute` | 开始执行、完成、归档（带版本号） |
| `POST /api/gf/docs/:id/cc-read` | 知会标已读 |
| `GET /api/gf/specials` | 微信特批列表 |
| `POST /api/gf/specials` | 登记微信特批 |
| `POST /api/gf/specials/:id/backfill` | 特批补登 |
| `GET /api/gf/files/:id` | 下载补登的文件 |
