## 2. 认人与安全

- 商城后端在请求头 `x-mall-key` 里带服务密钥（`.env` 的 `MALL_API_KEY`，至少 32 个字符，`compose.yaml` 已传进容器），在 `x-mall-staff-id` 里带员工编号，可选 `x-mall-store-id` 带门店编号。
- 密钥按摘要常量时间比对；没配密钥时所有 `/api/erp/mall/*` 回 `503 MALL_NOT_CONFIGURED`，密钥不对回 `401 MALL_KEY_REJECTED`。
- 每次请求按员工编号**现拼账号**（与浏览器会话同一套：岗位权限、店主的调整、能进的门店），员工在 ERP 里停用、撤了权限马上生效；要先改密码、选岗位的，业务接口照样拒绝（`PASSWORD_CHANGE_REQUIRED`、`POSITION_REQUIRED`）。
- 商城的接口**不读浏览器 Cookie、不做浏览器来源检查**（服务端之间调用）：拿着员工的 Cookie、不带密钥进不来；别的接口的来源检查照旧。
- 「采购需求单」模块关着时，商城接口一律 `403 ERP_MODULE_DISABLED`（登录校验也是）。
- 频率限制按商城后端的 IP 算（每分钟 300 次，`RATE_LIMIT_IP_PER_MIN` 可调）；门店设了访问网段（`ALLOW_CIDRS`）的，要把商城后端的地址加进去。
- 登录校验成功、失败都记审计（`login` / `login_failed`，`detail.channel = 'mall'`）；登录限次按 `clientIp`（商城转来的员工 IP）算。

## 3. 接口（前缀 `/api/erp/mall`）

| 方法与路径                              | 权限              | 说明                                                                                                                     |
| --------------------------------------- | ----------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `POST /auth/verify`                     | 只要密钥          | `{ username, password, clientIp? }` → 身份（员工、部门、我当主管的部门、能进的门店与主体、能做什么）                     |
| `GET /staff/me`                         | 账号在用          | 刷新身份；要改密码、选岗位的照样返回，标着                                                                               |
| `GET /master/meta`                      | 提 / 审 / 核库    | 在用的部门（带主管）、门店（带主体）、主体、用途、三档优先级、截单规则                                                   |
| `GET /master/materials`                 | 同上              | 在用的受管物料                                                                                                           |
| `GET /master/suppliers`                 | 同上              | 在用供应商：编号、名字、联系人、准入状态、更新时间——**不给银行账户、电话、证照**                                         |
| `POST /requests`                        | 能提需求          | 建需求单，见第 4 节；新建 201，原样重提 200 + `replayed: true`                                                           |
| `GET /requests`                         | 提 / 审 / 核库    | `status`、`departmentId`、`source=mall`、`updatedSince`（按进度时刻）、`from`、`to`、`limit`（≤ 200）；按 ERP 的可见范围 |
| `GET /requests/:id`                     | 同上              | 详情：给商城看的状态、退回原因、审批流水、每行进度                                                                       |
| `GET /requests/by-external/:externalNo` | 同上              | 按商城单号查                                                                                                             |
| `GET /requests/by-key/:key`             | 能提需求          | 超时后按操作编号查回：`{ found, abandoned, request }`；只能查自己的                                                      |
| `POST /requests/batch-status`           | 提 / 审 / 核库    | `{ ids?, externalNos? }`（合计 ≤ 100）；看不到、没有的列在 `missing` 里（不区分）                                        |
| `POST /ops/:key/abandon`                | 能提需求          | 确认作废一个操作编号：晚到的原请求回 `409 OP_ABANDONED`；已经建好的不能作废                                              |
| `POST /images`、`GET /images/:id`       | 提需求 / 提审核库 | 与 ERP 同一套图片（JPEG、PNG、WebP，≤ 1 MB），部门隔离照旧                                                               |

**可见范围**与 ERP 一样：部门申购看本部门的、自己提的、自己当主管的部门的；审核、核库的看全部。看不到的单一律 404（不区分是不是存在）。

**给商城看的状态**（`displayStatus` 与 `displayLabel`，`@shared/mall`）：待主管确认、待核库、待部门确认替代、待采购审核、已退回、不采购、已撤回、已转领用、已通过待下单、询价中、已下单、部分到货、已到货、已关闭。列表与批量查状态只按行数统计合（看不出「询价中」），要准的看详情。`progressUpdatedAt` 是审批流水、采购单、收货退货、询价、核库里最晚的一次变动，商城按它判断要不要刷新。

## 4. 建需求单

请求体（金额整数分、数量千分之一单位）：`clientKey`（UUID，商城提交前存好）、`externalNo`（商城申请单号，1–64 字，全局唯一）、`departmentId`（部门账号可不填，填了要是自己的部门）、`contactName`（实际经办人）、`storeId`、`entityId`、`budgetProject`、`needBy`（不早于今天）、`deliveryAddress`、`paymentIntent`（`company_direct` / `dept_petty`）、`priority`（`urgent` / `high` / `normal`）、`note`（≤ 500）、`lines`（1–50 行：`materialId`、`supplierId`、`mallSkuCode`、`priceVersion`、`name` ≤ 100、`purpose`（空着按「其他」）、`qtyMilli`、`unit`、`refPriceCents`、`taxRateBp`、`freightCents`、`link`、`details` ≤ 1000、`brandModel`、`expectedCategory`、`reasonText`、`note`、`imageIds`）。

- 同一个 `clientKey` 原样重提给第一次建好的那张；内容不同 `409 IDEMPOTENCY_CONFLICT`；换了 `clientKey` 用同一个商城单号 `409 EXTERNAL_NO_EXISTS`（`details.docNo` 是已有的单号）。
- 加锁顺序与 ERP 填单相同（`docs/LOCKING.md`「部门需求单」）。
- 物料要在用、受管；意向供应商要在用；新产品不要求链接与图片。
- 建好以后：要主管确认的等主管（主管本人用自己的账号提的算已确认）；不用的进核库（较急、普通照常核，紧急不核）。

## 5. 数据（迁移 `270`）

`purchase_requests` 加来源「商城」、三档优先级、`external_no`（唯一）、经办人、门店、主体、预算项目、收货地点、拟定支付方式，备注放宽到 500 字；`purchase_request_lines` 放宽品名、详情、链接、备注、申请人的长度，加 SKU 编码、价格版本、品牌型号、预期分类、采购理由、运费、税率。来源与商城单号建了以后不能改（守卫触发器）。回滚 `docs/rollback/270_mall_integration.down.sql`。

## 6. ERP 页面

需求单列表写「商城 + 商城单号」；详情顶上有「商城」标签，下面一行经办人、门店、主体、预算项目、收货地点、拟定支付；每行写 SKU 与价格版本、品牌型号、预期分类、税率、运费、采购理由，意向供应商写明「部门选的，仅供参考，以采购确认为准」。转采购单时意向供应商照旧带出。填单页的优先级多了「较急」（黄点）。

## 7. 用例

`tests/mall-integration.test.ts`：没配密钥、密钥不对、只带 Cookie；登录校验与审计、停用、要改密码；跨站来源；主数据与供应商脱敏；选品 + 自主申请建单（来源商城、较急、要主管确认、自检照过）；原样重提、内容不同、商城单号去重、按编号与商城单号查回；确认作废后晚到的请求被拒；只能给本部门提、日期、停用的供应商；部门隔离、采购看全部、主管确认 → 退回带原因 → 商城看到；三档排序；模块关着一律拒绝。

## 8. 后面（商城那一侧，另立项目）

店主答复「先让 AI 默认做」：商城后端（BFF）由 AI 来做，作为单独的项目（不放进 yuzu 仓库，yuzu 只提供上面的接口）。要先定：部署在哪（与官网同一台还是单独一台；要 ICP 备案、HTTPS）、商城自己的数据库、员工登录态怎么保存（建议商城自己的会话 + 每次调 yuzu 时带员工编号）、测试服的 `MALL_API_KEY` 与测试账号（每个部门一个申购账号）。首个验收节点照交接说明：测试服跑通一笔——部门测试账号登录商城并提交，ERP 产生一张需求单，采购审核或退回，商城显示同一张单的结果。
