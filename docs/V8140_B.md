# 8.1.40（B）：房态排序与过夜筛选、排位调到某人前面、一次派多张手牌

店主之前列的四条（`docs/ROADMAP.md` 第 7 节 8.1.40）。原来的流程都不变：不用新功能的店照旧那样用。没有新迁移、没有新的操作编号类型。

## 1. 房态中心：房号从大到小排

- 房态中心筛选条加「房号从小到大 / 房号从大到小」。从小到大就是原来的顺序（楼层、房号）；从大到小按房号倒排，数字按数值比（A102 在 A99 前面）。
- 只在页面上排（`@shared/room-center` 的 `arrangeRooms`），接口不变；总览、房型页签、搜索结果都按它排，每个分组里各自排。
- 选的排法记在这台设备上（浏览器本机存储 `yuzu.roomCenter.order`，读写都包了 try/catch：存不进只是下次打开回到默认）。

## 2. 房态中心：只看过夜

- 卡片上原来就有「过夜」小标（客人登记、续钟时选的过夜）。筛选条加「只看过夜 N」：只列有过夜客人的房间，N 是当前页签里有过夜客人的房间数。
- 与状态筛选、搜索一起用；记在地址里（`?overnight=1`），刷新、返回都还在。筛完一间都没有时写「没有……有过夜客人的房间」，点「看全部」清掉两种筛选。

## 3. 排位调到某人前面

- 钟房轮钟排队每一行加「调到…前面」：选同工种在岗队列里的一位、写原因（2–100 字，快捷原因在「数据字典」`queueMoveReasons`），这位技师直接排到他前面。
- 接口：`POST /api/clockroom/technicians/:id/move-before`，`{ clientKey, beforeId, reason }`，权限与「排到队尾」相同（`technician.dispatch`），返回新的看板。
- 带操作编号（合并前 Codex 审查 fca1ba4）：与休假、停牌、复牌同一类 `technician_state`。没收到结果时对话框里留着原请求：查回、原样重提（同一编号不会再调一次）或确认作废；处理好之前这位技师不能再调，确认作废以后迟到的原请求拒绝（`OP_ABANDONED`）——不然超时的那一笔迟到生效，会把之后另调的顺序盖掉。
- 排位就是 `technician_status.queue_key`：调到 B 前面＝改成 B 的减 1 毫秒；B 前面那位与 B 挤在同一时刻（或只差 1 毫秒）时，从他往前依次各提前 1 毫秒——只往前挪、相对顺序不变，B 和后面的人不动（`clockroom-queue.ts` 的 `moveBeforeKeys`）。已经就在他前面的不改、不记日志。
- 锁：只拿技师队列锁再写技师状态（与排到队尾相同，`docs/LOCKING.md` 第 1 节）。日志记一条「调整排位」：`调到 02 号前面：原因`（`detail: { reason, before: 工号 }`）。
- 拒绝：

| 错误码                       | 情形                                         |
| ---------------------------- | -------------------------------------------- |
| `REASON_REQUIRED`（422）     | 原因少于 2 个字                              |
| `MOVE_SELF`（422）           | 调到自己前面                                 |
| `NOT_ON`（409）              | 要调的这位不在岗（暂离、休假、停牌、未上牌） |
| `TARGET_NOT_ON`（409）       | 选的那位不在排位里                           |
| `QUEUE_KIND_MISMATCH`（422） | 两位工种不同（排位按工种分开，8.1.38）       |

## 4. 一次给多张手牌派钟

- 钟房顶上加「一次派多张」：每行一张手牌、一个项目、点钟 / 轮钟、一位技师（各 1 钟），最多 10 行；上面列着还没派钟的在店手牌，点一下加一行。一起提交，有一行不行就都不派，提示写明是哪张手牌。
- 只派新的一钟（挂账）。前台已经点了、等钟房派技师的（待派钟）照旧在「待派钟」里一条条补派、不另收费；某一行与待派钟同一位客人、同一个项目时行下面提示去补派。价格档按技师等级或项目的第一档；选别的价格档、选房间、按预约派请用单张派钟（接口每条都收这几项，页面上没放）。
- 接口：`POST /api/clockroom/dispatch-batch`，`{ clientKey, entries: [...] }`，每条与单张派钟（`POST /api/clockroom/dispatch`）的字段相同、只是不带 `clientKey`；权限也相同（`technician.dispatch` + `frontdesk.operate`）；最多 10 条（多了 400），同一张预约出现两次拒绝（`BATCH_BOOKING_TWICE`）。
- 规则：一个事务，按来访编号从小到大（同一位客人的按提交的先后）逐条走单张派钟的挂账 `postChargesTx`——价格、技师能不能做、休假停牌、轮钟排位与跳过原因（`SKIP_REASON_REQUIRED`）、技师预约、房间、预约到店一条不少；前一条派出去的技师在后一条里已经在钟上（同一位技师在一批里派两次轮钟，第二次 `TECHNICIAN_BUSY`）。每条错开 1 毫秒记时间，派了轮钟排到队尾时按这一批的先后排。某一条出错时错误码照旧（`PRICE_CHANGED`、`SKIP_REASON_REQUIRED`……），提示前面加「手牌 X：」、后面加「（这一批都没有派）」，`details.entry` 是提交的第几条（从 0 数）。
- 锁：先锁这几位客人的来访（id 升序）→ 账单（id 升序），再逐条走挂账（技师队列等在账单之后），不会反向加锁（`docs/LOCKING.md` 第 1 节）。
- 操作编号：整批一个编号，记成挂账 `bill_post`（查回、确认作废都走前台的 `/api/frontdesk/ops/:key`，查回给第一位客人的来访）；原样重提返回成功、不重复挂账，同一编号换了内容 `IDEMPOTENCY_CONFLICT`，确认作废以后原请求迟到 `OP_ABANDONED`。每一条的明细另用由整批编号推出来的编号（`entryKey`，固定）。所以不用给 `idempotency_keys` / `op_fences` 的类型约束加新类型、没有迁移。
- 页面上与单张派钟同一套「结果待确认」：提交前本机记下编号与原请求，这几张手牌上都不能另起一笔挂账，关掉对话框再开照样看得到那一笔。

## 5. 用例

- `tests/clockroom-v8140.test.ts`（集成）：调位的算法（有空隙、同一时刻、连着挤）；调到前面 / 后面 / 队首、已经在前面不变、原因必填、暂离 / 未上牌 / 不同工种 / 调到自己拒绝、没有钟房权限 403；同一时刻的几位调开以后轮钟按新排位派；批量派按来访先后算轮钟、按批内先后排尾、明细的编号、原样重提不重复、查回、换内容冲突；一条不行整批不派（跳过没写原因、价格变了、同一位技师两次轮钟）、写了原因能跳过、最多 10 条；确认作废以后原请求不生效；没有前台挂账权限 403。
- `tests/room-center-v8140-shared.test.ts`（秒级）：排序（默认照原顺序、倒排按数值比、不改原数组）与只看过夜。
- 三台设备：调位对话框、一次派钟对话框是普通弹窗（窄屏一行两列、宽屏一行五列）；房态筛选条的按钮在窄屏换行。没有在真机上看。
