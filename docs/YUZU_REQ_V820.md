## 3. P02 侧边栏固定，内容区独立滚动（2-1）

- 门店页面（前置操作平台，`AppShell`）：整屏不滚（`h-dvh overflow-hidden`），左侧主导航撑满一屏、固定不动，菜单长了在导航里面滚；右边内容区（`data-testid="app-content"`）自己滚，滚动条统一用细滚动条。页面自己有滚动区的照旧在里面滚，内容区不会再出第二条滚动条。
- 页头（`PageHeader`）贴在内容区顶上（`sticky`），内容区滚动时页头、导航都不动。
- 收起成一列图标时：鼠标停在业务域上就弹出二级入口（触屏照旧点一下弹出），移开稍等一下收回；停出来的再点一下是留住，不是关掉。
- 窄屏（1024 像素以下）：平时一列图标；点「展开导航」是盖在内容上的抽屉（内容不挤开），带遮罩，点遮罩、按 Esc、换页面都收回。原来 768–1024 之间展开是挤开内容的侧栏，手机不能展开，现在都是抽屉。
- 层级：页头 20、遮罩 30、抽屉与弹出的二级入口 40、弹窗 50、提示 60 以上；弹窗、下拉框不被导航盖住。
- 后台（`AdminShell`）与 ERP（`ErpShell`）原来就是「左侧固定 + 右侧滚动」，1024 以下是顶上一排分区页签，这次没动（RT4）。
- 用例：`e2e/layout-820.spec.ts`。

## 5. P04 岗位职权数据重建（5-2 的数据部分）

迁移 `201_position_catalog.sql`：
- **三张表**：`org_departments`（部门）→ `position_catalog`（岗位：所属部门、岗位名、管理员级别、排序；总裁标「全部权限」）→ `position_suggestions`（每个岗位的建议权限）。初始数据按最新的岗位职权表（8.1.18《组织架构与岗位体系》表 3），与代码里的 `positionDefaults` 逐项一致（`tests/position-catalog.test.ts` 在迁移完的库上核对）。之后在后台页面维护（P05），不用再找开发。
- **同一个岗位名在不同部门**是不同的岗位（键是「部门.负责人 / 员工」），各自一份建议权限，互不影响。
- **算权限**：建议权限（库里的）→ 「设立岗位」按岗位的增减（`settings.position_permissions`，原样保留，意思不变）→ 个人微调。会话每次请求按库里的算，改完下一次请求就生效。库里没有这个岗位时（不该有）按代码里的模板。
- **配置日志** `position_config_log`：只追加；迁移时记一条 `init`（几个部门、几个岗位、几项建议权限）与一条 `legacy_migrate`（还在用旧岗位、专用账号各几个）。P05 起每次改动记一条（操作人、时间、改了什么）。
- **旧岗位与专用账号**（RT11）：不删、不改任何账号与历史。旧岗位那张表（`settings.role_permissions`）原样保留，只对专用账号（点餐平板、他店查询、设计师）与还在用旧岗位的老账号生效；8.1.18 起老账号登录时自己选岗位（迁移 194 已标好），迁移 201 只在配置日志里记一笔各有几个。
- **回滚**：`docs/rollback/201_position_catalog.down.sql`。回滚以后算权限回到代码里的模板（与初始数据一致），「设立岗位」的增减、个人微调、旧岗位表都不受影响；P05 页面上改过的建议权限会丢，回滚前先导出 Excel 留底。
- **以后加新权限**：除了代码（`permissions.ts`、`positions.ts`），还要写迁移往 `position_suggestions` 里给该有的岗位加上（新库按迁移初始化，`tests/position-catalog.test.ts` 会核对代码与迁移一致）。

## 6. P05 分部门岗位职权配置页（5-2 的页面部分）

后台「岗位权限」的第二个页签换成「分部门岗位职权配置」（`?tab=catalog`，`PositionCatalog.tsx`，接口 `src/server/modules/position-catalog.ts`）：
- **按部门列出岗位**：岗位名、管理员级别、建议权限几项、配置状态（已配置 / 未配置；「设立岗位里改过」另标）、在职人数；按部门或岗位名搜索。总裁固定全部权限，不在列表里。
- **页面维护**：选一个岗位，按模块分组勾选它的建议权限（单项、全选、全不选、反选、本组全选、搜权限；与保存的不同的项标黄），「保存建议权限」整批换，立即生效。有没保存的修改时换岗位，先弹「是否放弃当前修改？」。保存带这个岗位的版本，别人先改过拒绝（`POSITION_STALE`），页面重新取。只有「修改经营规则」（总裁）能改，能看审计的只能看。
- **同一岗位在不同部门**各是一行、各自一份（比如男宾部员工、女宾部员工）。
- **导出 Excel**（`分部门岗位职权配置-日期.xlsx`）：「职权表」一行一项权限、一列一个岗位（两行表头：部门、岗位），建议的打 ✔，与原始表格逐条核对；「岗位汇总」；「变更记录」。
- **变更留痕**：每次保存记 `position_config_log`（操作人、时间、加了与去了哪几项），另记审计（`settings_updated`，对象 `position_suggestions`）；页面下方列出最近 100 条。
- **旧岗位与专用账号**：这一页下方一张卡片说明，点「打开旧岗位表」进原来的旧岗位那张表（`?tab=roles`，专用账号与还没选岗位的老账号照旧按它，照旧能改），有「回到分部门岗位职权配置」。
- 加锁见 `docs/LOCKING.md`「分部门岗位职权配置」。
- 用例：`tests/position-catalog.test.ts`（列表、改与日志、版本、权限、导出）、`e2e/position-catalog-820.spec.ts`。

## 7. P06 选岗位联动建议权限（5-1）

后台「岗位权限 → 设立岗位」（`PositionPermissions.tsx`）：
- **选岗位就带出这个岗位的权限**：勾选按这个岗位保存过的权限重置（没在「设立岗位」里改过的就是建议权限）。建议权限从库里来（P04 的 `position_suggestions`，「分部门岗位职权配置」维护），前端不写死。岗位旁边写管理员级别、建议几项、「按建议」或「已按岗位调整 N 处」。
- **换岗位前先问**：改了没保存时换岗位，弹「是否放弃当前修改？」——「继续改」留在原岗位、勾选不动；「放弃修改」换过去、丢掉草稿。
- **按模块分组**：与 P05 共用 `PermissionPicker`（按权限表的模块分组；单项勾选、全选、全不选、反选、本组全选 / 全不选、搜权限）；只属于总裁的带锁、不能勾。
- **与建议不同的项**标黄底和「与建议不同（建议有 / 没有）」，组标题写这一组差几项，顶上写一共差几项；「恢复建议权限」一键回到建议（还要点「保存这个岗位」才生效）。
- **回显与不串台**：草稿连同岗位一起记，不是当前岗位的草稿一律不用，换岗位的那一刻也不会把上一个岗位的勾选带过去；保存后用服务端返回的结果刷新，换走再回来、刷新页面都照保存的显示。
- **员工账号**：添加 / 编辑员工时，权限照旧跟着选的岗位走（「按岗位自动套用 N 项权限」）；给这个人逐项微调过再换部门或岗位，先问「是否放弃当前修改？」（微调是相对原岗位的，换岗位就清掉）。
- 接口、数据不变（`PUT /api/admin/position-permissions` 照旧存相对建议权限的增减）。
- 用例：`e2e/position-setup-820.spec.ts`（换岗位带出建议、先问、标出不同、恢复建议、保存回显、不串台；员工账号换岗位先问）。

## 8. P07 房态点单后端（3-1 的服务端部分）

房态中心「在用」的房间直接点水吧、果吧（`src/server/modules/room-orders.ts`、`@shared/room-orders`，迁移 `202`，默认做法 RT15–RT20）：
- **下单**（`POST /api/room-center/rooms/:key/orders`，`key` 是卡片的 `s<空间>` / `r<客房>`）：挂到房里现在那位客人的手牌账单上，与点单页同一个挂账（`postChargesTx`）——只能点进厨房的菜、价格以服务端为准、核对确认时的合计（`PRICE_CHANGED`）、扣沽清、出出品单；出品单的「送到哪」写「房 H601」，每行的口味备注与整单备注印在出品单上（出品屏、自动打印照旧）。
- **只能点在用的房间**：没有客人、在维修的拒绝（`ROOM_NOT_IN_USE`）；来访锁住以后再核对一次这间房还是这位客人（`ROOM_GUEST_CHANGED`）。
- **一单只点一个出品口**（面板上的水吧 / 果吧两个页签）：别的出品口、餐厅的菜整单拒绝（`ROOM_ORDER_OUTLET`）；逐行按出品口核对下单权限（`OUTLET_FORBIDDEN`，与点单页同一个函数）；不在门店配置的分类里的拒绝（`ROOM_ORDER_CATEGORY`）。
- **不会重复**：操作编号按出品口单独成类 `room_order_water` / `room_order_fruit`（迁移 202 在当时的约束上追加；不与挂账 `bill_post` 共用，水吧、果吧也分开——只有一个出品口下单权限的人确认作废时，碰不到别人的挂账，也碰不到另一个出品口的点单，Codex 安全审查 e1c3203、404eb2f）。同一编号原样重提返回第一次那一单、不再挂账，换了内容拒绝（`IDEMPOTENCY_CONFLICT`）；断网后的「结果待确认」在 `/api/room-center/order-ops/:outlet/:key` 查回、确认作废（要那个出品口的下单权限；别的业务、另一个出品口的编号只答「没查到」、不作废）。
- **记录**（`room_orders`、`room_order_lines`，只追加）：哪间房、当时的房号、挂在哪位客人上、出品口、出品单号、整单备注、下单时的合计、经办人（工号与姓名）与时间；挂到账单的哪几行。
- **点单记录**（`GET /api/room-center/rooms/:key/orders`）：最近 100 单，逐行写有没有退、谁退的、为什么；`current` 是房里现在的客人点的单数与金额。
- **卡片**：房态中心看板每间房多一个 `orders`（房里现在的客人从房态点了几单、多少钱，退掉的不算；没点过为空）。
- **撤单**：就是作废那几行账单明细（`POST /api/frontdesk/lines/:id/void`，要原因；康美部有「退菜：水吧 / 果吧的菜」，逐行按出品口核对，超过小额上限照规矩要授权，留审计），不另做一套。
- **权限**：点单要「在水吧下单」或「在果吧下单」（康美部的建议权限里本来就有）；看点单记录另外允许能看房态的岗位。房态中心看板也对这两项权限开放（RT20），但只有这两项的只拿到精简的卡片（房号、名称、状态、这次在用点了几单与多少钱），不给客人、手牌与来访、技师与钟、金额、客房房价与押金、预约与维修说明；房间历史等其余接口照旧要原来的权限（Codex 安全审查 e1c3203）。
- **按出品口配置能点的分类**（`GET/PUT /api/admin/room-order-config`，改要「修改经营规则」）：水吧按点单小分类、果吧按价目分类，列出菜单里现有的分类来勾；不勾为全部；改动记审计。面板读 `GET /api/room-center/order-config`。
- 加锁见 `docs/LOCKING.md`「房态点单」。回滚脚本 `docs/rollback/202_room_orders.down.sql`（删三张表；点过的单照旧在账单与出品单上）。
- 用例：`tests/room-orders.test.ts`（下单挂账与出品单、卡片、原样重提、空房 / 别的出品口 / 合计对不上 / 无权限、分类配置、撤单与记录）。
