## 1. 扩钟单独一类

- 上钟方式从「轮钟 / 点钟」变成三种：**轮钟**（rotation）、**点钟**（designated，场内点名）、**扩钟**（call，场外预约：客人约好后到店）。明细 `bill_lines.call_type` 与钟单 `technician_sessions.call_type` 的约束放宽（`540`，先 `NOT VALID` 再 `VALIDATE`）。前台挂账、钟房派钟、批量派钟、转钟、补派、房态中心的上钟方式都多一个「扩钟」。
- **排位不动**：扩钟派钟时不排尾、下钟（含结账时一起收尾）也不排尾——上牌时排第几，做完还是第几（`clockroom.ts` 里派钟、下钟的两处 `toEnd` 只认轮钟、点钟）。「点钟期间轮到了就排尾」的规则也不算扩钟。
- **从预约派出的钟默认记扩钟**（钟房「预约到店」带进派钟对话框时默认选扩钟），派钟时可以改。扩钟不查这位技师别的预约（他同时约了几位客人，上的就是其中一位；`booking-guard.ts` 的冲突检查对扩钟跳过）。
- **加钟单列**：加钟不是上钟方式（照旧按「加钟记为点钟」规则记 call_type），在明细上记 `clock_extension = true`（挂账时由钟房加钟、房态中心续钟写定；转钟、转单时照抄）。报表里点钟、轮钟、扩钟都**不含**加钟，加钟单列一列。
- **报表**：`GET /api/reports/technicians` 每行与合计多 `call`、`extension`；看板「技师业绩」表多「扩钟」「加钟」两列，钟房看板顶上的今日统计多 `call`。提成明细导出的「上钟方式」写轮钟 / 点钟 / 扩钟 / 加钟。
- **提成**：规则多 `callBonus`（扩钟每钟另加，**不填与点钟奖励一样**），后台「技师 → 规则 → 技师提成」单独设。

## 2. 一报多

- 预约页加「一报多」按钮（`features/bookings/BatchBookingDialog.tsx`）：默认 **3 行**，「再加一行」最多 **10 行**（`MAX_BATCH_BOOKINGS`）；每行客人姓氏、手牌号（可空）、电话（可空）、项目、技师（可「不指定」）、时间；整批选一天与来源（前台 / 电话）。
- `POST /api/bookings/batch` `{ clientKey, source, rows[] }`：一个事务、一个操作编号（记成 `booking_create`，查回给第一张），**全部建好或一张都不建**；哪一行不行，提示写「第 N 行（姓氏）：…（这一批都没有建）」、`details.row` 是第几行（从 0 数）。每行用整批编号推出来的编号（`batchRowKey`）记在预约单的 `client_key` 上，原样重提返回同一批。
- **一位技师同时约几位客人不设上限**：一报多里指定了技师的行不查他同一时段别的预约，只查他能不能做这个项目；不指定技师的照旧要有空着的技师。单张新建预约照旧查重叠。
- 手牌号记在 `bookings.tag_code`（`540`，格式与发牌相同，可空），预约列表里写「报的手牌」；不锁手牌，到店时照旧在「到店」里登记手牌。
- 前台有没有技师预约权限属于批 3，这里不动权限。

## 3. 退技师

- 新权限 **`technician.voidLate`「超时退技师」**：默认店主、店总、值班经理（`permissions.ts`）；按部门的岗位里给前厅、娱乐、康养负责人与总经办（`positions.ts`，`540` 同时把建议权限写进库、各记一条配置日志）。
- 退钟 / 取消派钟（`voidSession`）改用 `clockroom-change.ts` 的 `assertCanVoidSession`：有「超时退技师」或「作废与撤销」的随时能退；其他人照旧只能退自己挂的、更正时限内的（前台规则 `selfVoidMinutes`，默认 15 分钟）。
- 超时、不是本人挂的，回 403 `VOID_LATE`，提示**改走退项**：「请当班管理层（值班经理及以上）在钟房退钟；或者走退项：在收银台打开这张手牌的账单，把这一项作废并写原因（要值班经理及以上确认），已经结账的开退款单」。不再写「请由店主处理」。

## 4. 换项目 / 换工种

- 钟房的钟单（上钟中、已派待上）多一个「换项目」（`ChangeItemDialog.tsx`），`POST /api/clockroom/sessions/:id/change` `{ clientKey, itemId, tier?, quantity, technicianId?, callType?, reason, skipReason?, expectedTotal }`。
- **时限**：上钟后 **15 分钟内**能换（钟房规则 `changeItemMinutes`，后台可改 0–120）；还没上钟的随时能换；满了回 `CHANGE_TOO_LATE`，提示先退钟再重新派。
- **同一位技师能做新项目**：原明细作废（原因「换项目：…」），按新项目挂一条（价格、能不能做都走前台挂账的核对），钟单改成新项目、钟数与计划时长按新项目算，上钟时刻照旧、**排位不动**。
- **换工种**（原技师做不了新项目，或店员另选了技师）：原钟单收尾（没上钟的记取消、上了钟的记被退，原因「换工种：…」），原技师**回到派这一钟之前的排位**（`queue_key_before`），**不算被退钟次数**；新技师按派钟的规矩上（轮钟要轮到他、跳过写原因），原来在钟上的马上上钟、房间照旧。
- 两种都记在 `technician_session_changes`（只追加），钟房日志记「换项目」，看板上钟单标「换过项目」，审计 `clock_change`。
- 锁与退钟、转钟同一个顺序：来访 → 账单 → 原明细 → 技师队列 → 原钟单 → 技师状态 →（新明细、钟单）。带操作编号（`bill_post`），走「结果待确认」。

## 5. 休假

- **钟房的休假入口直接设天数**（`TechStateDialog`）：1 天照旧只管今天（上牌即取消）；2 天以上记成一张休假单（`POST /api/clockroom/technicians/:id/leave-days`，最多 31 天，与技师管理的休假单同一张表）。有「维护技师名册」的**直接批准**（今天起就是休假）；没有的记成**待审批**，等技师管理批准，今天照旧。
- **到期自动上牌**：休假单多 `auto_return`（默认是）、`returned_at`。每分钟的任务（`jobs.ts`「技师休假到期上牌」，`technician-leave-return.ts`）看已批准、休完了、还没处理的单，在**休完后的第一个营业日**给他上牌、**排到队尾**，钟房日志记「休假到期，自动上牌、排到队尾」（经办人「系统」）。选每分钟任务而不是读的时候判断：排到队尾要有一个确定的时刻，读的时候算每次都不一样。
- 那天已经有人动过他的状态（手动上牌、下牌）、又在另一张休假里、今天排休、停牌、停用的不动，只记下处理过；休完超过 7 天才看到的（应用停了很久）不补上牌。钟房规则 `leaveAutoReturn` 可以整体关掉。

## 6. 状态

- 钟房的状态筛选与「按状态排」对齐纪要的叫法：**空闲、待中（已派待上）、上钟、已带、暂离、休假、未上牌**，另有停牌。
- **已带**的定义：今天已经做过钟（今天有没作废的技师明细）、现在在岗、手上没钟——还在排位里等下一钟。空闲是在岗、手上没钟、今天还没做过钟。按状态排时空闲在前、已带其次（`techFilterOf(t, true)`）。大屏、榜单、派钟对话框照旧只分到「空闲」（不传第二个参数）。

## 7. 统计

`technician-stats.ts`，看的三项要「看技师业绩」；看板「技师业绩」页签下面新加一块（`TechnicianStats.tsx`），选一个月：

- **每天的扩钟数**（`GET /api/reports/technicians/calls?from&to`，最多 62 天）：按技师、按天；按挂账口径（没作废的扩钟明细，不含加钟，客人还没结账的也算），当天就能看。
- **每 10 天一段的总业绩**（`GET /api/reports/technicians/periods?month`）：1–10、11–20、21–月底三段，所有工种，按工种（技师档案的「类型」）小计；按结账口径，与技师业绩同一份明细。
- **每月业绩任务**（`technician_targets`）：按技师或按组设目标金额与目标钟数（`PUT /api/admin/technician-targets`，要「维护技师名册」，整月替换，审计记改前改后）；`GET /api/reports/technicians/targets?month` 给完成度（结账口径，本月算到今天；按组设的算组里现在的成员）。
- **财务**：「看技师业绩」「看技师提成」两项加上财务职责（对账付款、成本核算）；财务部负责人的建议权限加「看技师业绩」（原来只有提成）。

## 8. 网页导入技师、技师档案、按星级与门店的提成

- **技师档案**加手机（`phone`，11 位）、身高（厘米）、体重（公斤）、星级（1–10）。手机号**只给打码的**（`@shared/mask` 的 `maskPhone`）：后台名册返回 `phoneMasked`，技师管理名册只给能改名册的；编辑时留空不改、可以清掉；审计里也打码。
- **网页导入**（后台「技师 → 技师名册」下面的「导入技师」，`technician-import-web.ts`）：上传 Excel / CSV，自动认表头（姓名、工号、花名、电话、组别、身高、体重、星级，及原来认的技师号、昵称、技师组别、技师等级、入职日期等别名；表头前面有说明行也认），**先预览逐行核对**，有一处问题**一行都不写**。工号本店没有的新建（表里没写性别的按页面上选的，没选的报出来要补）；已有的只更新表里有值、和名册不一样的花名、电话、组别、身高、体重、星级（格子空着是不改；姓名、性别、等级、入职日期不改，有出入的写在预览里）。生效带回预览的摘要，预览以后名册或文件变了就拒绝。**原样再导结果一样**（都是「不变」）；结果不明时重新预览就看得出导没导进去。提供模板下载（第一行填写须知、第二行表头）。命令行 `import-technicians` 照旧，新建时也写这四列。
- **提成按星级**：原来星级在导入时并成 3 个价格档（`--grade-map`），价格档照旧决定价格；现在另存星级，提成规则多 `stars`（按星级覆盖默认），**优先级：项目单独设置 → 星级 → 默认**。挂账时把技师那一刻的星级记在明细上（`bill_lines.tech_star`），之后改星级不影响已挂的钟。
- **各店各自的规则（「各地区不同」）**：提成规则版本多 `store_id`。保存时记成本店的；本店没保存过的照旧用原来全公司一份的（`store_id` 为空的旧版本）；多店合看的报表按每条明细结账单的门店取规则。

## 11. 8.2.4 的一报多预约补「有意重叠」标记（迁移 740，8.2.17 之后，不改版本号）

**问题**（店主）：升级以后前台自检「预约不重叠」把 8.2.4 一报多建的技师预约报成重叠。8.2.5 的迁移 `570` 加 `bookings.technician_overlap` 时历史预约一律是 `false`，自检（`bookingChecks`）只放过有标记的；8.2.5 起的代码给一报多的技师预约写 `true`，8.2.4 时建的没有。`570` 已发布，不改；新迁移 `740` 补，按出处认，不猜。

**出处（核对过旧代码）**：

- 一报多是 `ec4913b`（8.2.2 技师后端）写的，8.2.2、8.2.3 没有单独发版：`main` 上 `v8.2.0` → `v8.2.4` 只隔一次合并（PR #46），所以**写 `false` 的一报多只有 `v8.2.4` 这一个发布版本**。`v8.2.4` 与 `ec4913b` 的一报多部分一样（只多了 8.2.3 的看板按权限过滤）；`v8.2.4` → `v8.2.5`（`e3042ee`）只加了两处：写 `technician_overlap`、一报多先核对「技师预约」权限（`git diff v8.2.4 e3042ee -- src/server/modules/bookings.ts`）。
- `v8.2.4` 的 `createBookingBatch`（`src/server/modules/bookings.ts` 第 634–671 行）：整批一个操作编号 K（`clientKey`，前台 `lib/utils.ts` 的 `uuid()` 生成，小写），`runIdempotent(..., opType: 'booking_create')`，最后 `saveKey(tx, K, 'booking_create', hashRequest({ op: 'booking_batch', source, rows }), ids[0], 经办人)`（第 663 行）——编号记在 `idempotency_keys`：`op_type = booking_create`、`ref_id` = 第 1 行的预约、`staff_id` = 经办人。
- 第 i 行（从 0 数）的预约 `client_key = batchRowKey(K, i)`（第 624–627 行，与现在第 626–629 行逐字一样）：`sha256('booking-batch:' + K + ':' + i)` 的十六进制摆成 UUID——第 13 位写 `4`，第 17 位取低 2 位再或 `8`；每行都带 `technicianOverlap: true`（第 654 行），指定了技师的不查他同一时段别的预约（`claimSlot` 第 493 行），不指定的照旧要有空着的技师。行数最多 10（`MAX_BATCH_BOOKINGS`）。
- 单张新建的 `client_key` 就是它自己的编号（`ref_id` 是这张），推不出别的行编号；所以「库里有一条 `booking_create` 编号 K、某张预约的 `client_key` 正好等于 `batchRowKey(K, i)`」只可能是一报多写的（sha256 撞上的机会可以不计）。
- `idempotency_keys` 只追加（`001_init` 的 `idempotency_keys_append_only` 触发器，拒绝改与删）；8.1.47 的归档任务（`483_archive_tables`、`modules/archive.ts`）只挪位置事件、轨迹段、对外调用、企业微信推送四张表，**不碰操作编号**，也没有别的清理任务删编号。8.2.4 写的编号都还在，没有被归档或清掉的；对不上的只会是别的原因（见下「对不上的」）。

**740 怎么认**（函数 `yuzu_booking_batch_links()`，迁移与核对脚本共用）：对每条 `op_type = booking_create` 的编号 K、i = 0…9，用 `yuzu_booking_batch_row_key(K, i)`（与 `batchRowKey` 逐字一致，用例对 500 组核对）找 `client_key` 相等的预约。一批算确认，要同时满足：

1. 行号从 0 连续（找到的行数 = 最大行号 + 1；一个事务建的，不会缺行）；
2. 第 0 行就是编号记的 `ref_id`；
3. 每行都是技师预约（一报多只建技师预约）；
4. 每张的经办人（`created_by`）与编号的 `staff_id` 一致；
5. 来源是前台 / 电话、没有会员、1 位客人（一报多只会这样建）。

确认了的整批每张技师预约都标 `true`——与现在的代码一样（现在一报多的技师预约一律写 `true`，不指定技师的那行也是；8.2.4 定标记的规则与现在相同，8.2.5 多出来的只是「谁能建」的权限核对，不是写不写标记的条件，所以取交集还是这一条）。同一技师、同一时段、建的时间挨着都不算证据。只改 `technician_overlap`（只从 `false` 改 `true`），时间、状态、版本号等别的列都不动；每改一张记一条审计 `booking_overlap_backfill`（经办人为空，`detail` 写预约单号、整批编号、行号、迁移名）。重复执行：第二次没有要改的，也不再记审计。回滚 `docs/rollback/740_booking_batch_overlap.down.sql`：按这几条审计把它标的改回 `false`、删两个函数（审计只追加，留着）。

列的就是自检会报的那些（同一位技师、时段交叠、两张都还占着时段、两张都没标），每张写出处与「是不是 570 以前建的」：

- **单张新建（真的重叠）**：`client_key` 是自己的 `booking_create` 编号——普通预约，按数据错误处理；
- **找不到操作编号 / 编号记成别的操作**：导入、演示数据、手工补的或别的入口建的，没有证据是一报多；
- **一报多编号对得上但整批不全或不一致**（后面写哪一条没过）：编号推得出来，可上面 5 条有一条不成立（比如编号或预约被手工改过），要人看。
