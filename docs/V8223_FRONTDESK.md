# 8.2.3 前台：发卡台与全店（客人类别、偏好、客诉台账、拥挤与高风险提示、技师预约权限、跳转明细、同行移出、补单）

来源：会议纪要《会所管理系统演示与需求讨论》（2026-11-26 15:20）里前台的九条。照老规矩先看系统里有没有，有的补齐、没有的才做，不另起一套。迁移 `550`（号段 `550`–`559`，`docs/ROADMAP.md` 第 7 节已登记），回滚 `docs/rollback/550_frontdesk_guest.down.sql`。规则的默认值都能在后台「手牌与前台 → 客人与提醒」改（按店），拍板的做法列在第 10 节、`docs/PENDING_DECISIONS.md`「8.2.3 前台」QT1–QT12。

## 1. 客人类别（纪要「客人类型：需要增加港客、外宾、儿童等类别」「发手牌时可修改客人类型并备注预约技师」）

- 原来：只有男宾 / 女宾两个分区（`src/shared/frontdesk.ts` 的 `ZONES`）和散客 / 会员。分区是手牌柜，不动；类别另记一项。
- 做法：后台字典 `frontdesk_guest_rules.categories`（默认「普通、港客、外宾、儿童」，最多 12 个，可加可改名）。第一项是默认类别，手牌上不标。
- 发牌：接待发牌每位客人一行多一个「客人类别」下拉和「预约的技师（选填）」框。类别记在 `visits.guest_category`（记的是字，清单改了以前的照旧显示原来的字；空 = 默认类别）。预约的技师记成这位客人的一条单人备注（标签「预约技师」），这样全店刷手牌都看得到，不另建一套。备注的操作编号由发牌编号与第几位客人算出来，重提发牌不会多记。
- 发牌后改：客人卡「客人类别与偏好」那一块的下拉，`POST /api/frontdesk/visits/:id/category`，进经办记录（「客人类别 普通 → 外宾」）、审计 `visit_category`，记录只追加（`visit_category_changes`）。结了账的不能改。
- 全店显示：手牌板卡片、收银台待结账清单的状态小标（`VisitStatusChips`）多一个蓝色类别标（带字带图标）；点单、钟房派钟、房态中心见第 2 条的那一条。

## 2. 偏好备注全店可见（纪要「客户要求前台就能添加备注（忌口、按摩力度等），且全店刷手牌都能看到」）

- 原来：8.1.44 的前台备注（`visit_remarks`）挂在来访上，只在发卡台、收银台显示，不随会员到下一次，没有结构化字段。
- 做法：
  - 后台加偏好字段（`prefFields`，默认「忌口、按摩力度、其他」，最多 8 个）。每个字段有一个不变的编号（新加的自动生成），改名不丢以前填的值；删掉的字段以前填的值留在库里、不再显示。
  - 客人卡上「填偏好 / 改偏好」，`PUT /api/frontdesk/visits/:id/preferences`（只改提交的几格，填空 = 清掉），记审计 `guest_preferences`（改前、改后）。
  - **会员的偏好记在会员上**（`guest_preferences.member_id`，下次来自动带出）；**散客的记在这次来访上**（`visit_id`）。
  - 全店刷手牌的地方：新接口 `GET /api/frontdesk/guest-notes?visitIds=…`（有查看手牌、点单、派钟、客房任一权限就能读）给类别、填了的偏好、没撤下的备注（单人 + 所在同行组）、高风险。点单页找到客人后、钟房派钟填了手牌后、房态中心房间详情里每位客人下面，都显示这一条（`GuestNoteStrip`）；发卡台、收银台在备注板块上面（`GuestProfileCard`）。

## 3. 客诉台账（纪要「可备注客诉和特殊关照，计划做一键打印的台账」）

- 原来：客诉、特殊关照是备注的标签，收银台清单上有标；没有跨来访的台账。
- 做法：
  - 新页面「前台 → 客诉台账」（`/crm/complaints`，新权限「客诉台账」，默认值班经理及以上）：带客诉类标签（后台 `complaintTags`，默认「客诉、特殊关照」）的备注，按来访的营业日起止、状态（没处理 / 已处理 / 全部）、标签筛；门店按顶上的门店切换（「合并看」时是几家店，`storeIn`）。
  - 「标已处理」写处理结果（`visit_remark_resolutions`，只追加、一条只能标一次，再标回 `COMPLAINT_RESOLVED`），审计 `complaint_resolved`。撤下的备注照旧列出（划掉）。
  - 「打印台账」：A4 打印页 `/print/complaints/:from/:to/:status`（与台账页同一个接口）。

## 4. 区域拥挤提示（纪要「系统可根据区域人数提示换区发牌……可设定连续派出多少手牌后建议换区」）

- 原来：没有。
- 做法：接待发牌对话框里，牌号对上一张能发的普通柜时，算这张牌所在的区（牌号的字母前缀，A、B……；同一分区里算）：
  - 连续：这个分区在店的客人按发牌时刻倒着数，连着几张都在这个区；到了「连续往同一区发几张后提示」（默认 10，0 = 不按这个）就提示；
  - 人数：这个区在店人数到了「一个区在店超过几人提示」（默认 0 = 不按这个，门店量过换衣处再填）就提示。
  - 提示写明原因，并建议同一分区里在店最少、还有空牌的区，带一个「改发 B023」按钮。只提示，不拦（`@shared/frontdesk-v8223` 的 `crowdAdvice`，用的就是手牌板的数据，不另取）。VIP 柜不提示。

## 5. 高风险提示可配置（纪要「消费超 24 小时或金额超设定值（如 2000）时系统提示，防止跑单，需后台配置通知层级」）

- 原来：超时提醒固定 12 / 24 / 72 小时进「异常待办」（`overtime.ts`，不动）；没有金额阈值，没有通知层级。
- 做法：
  - 阈值：在店超过 X 小时（默认 24）、挂账超过 Y 元（默认 ¥2,000，不含门票，按这张手牌的账单），两个都能设 0 关掉。
  - 页面：发卡台的手牌卡片、收银台的待结账清单标红「高风险」（悬停写原因）；发卡台顶上「高风险 N 位」打开提醒列表（`GET /api/frontdesk/risk-alerts`），点一行打开那位客人。
  - 通知层级：只在页面上提示（默认）/ 推给值班经理、店总、店主 / 推给店总、店主。选了推送的，每分钟的任务（`sweepRiskAlerts`，`jobs.ts`「高风险提示」）给超了阈值、还没推过的客人推一次站内通知（`notify`，种类「系统」，点开到发卡台这张牌；登记了企业微信等外发通道的跟着发）。每位客人每一样（超时、大额）只推一次，`visit_risk_alerts` 的 `(visit_id, reason)` 唯一兜底，几个进程同时跑也只推一次。收件人：在职、挂在这家店（或没挂店）的这几个旧岗位（`staff.role`）。

## 6. 预约按种类分权限（纪要「客房和派对房公开，技师预约权限不给前台」）

- 原来：一个「预约」（`booking.manage`）管技师、派对房、客房三种。
- 做法：新权限「技师预约」（`booking.technician`）；「预约」只管派对房、客房（`@shared/bookings` 的 `BOOKING_KIND_PERMISSIONS`）。预约看板只列能做的那几种；新建、改、看单张、查时段按种类核对（403 写明要哪一项）。
- 默认：店主、店总、值班经理有；**收银员（前台）没有**（店主要求的）。按部门的岗位：前厅部员工没有，前厅部负责人、总经办有。
- 迁移 `550` 保持原能力：后台「岗位权限」（旧岗位 `role_permissions`、新岗位 `position_permissions`）里加了「预约」的岗位一起加「技师预约」（收银员、前厅部员工除外），去掉了「预约」的一起去掉；员工档案的个人微调加了「预约」的照旧能约技师；岗位建议权限（`position_suggestions`）里有「预约」的岗位加上（前厅部员工除外），各记一条配置日志。
- 不变：发牌时会员当天的技师预约照旧带出并标到店（那是发牌，不是改预约）；钟房按预约派钟照旧要「钟房派钟」。

## 7. 消费记录跳转明细（纪要的经办记录、消费明细）

- 原来：会员工作台的余额变动（`ActivityList`）只写结账单号文字。
- 做法：余额变动、流水接口多给 `checkoutId`；前台结账的消费行上「结账单 JZ…」可点，在右侧打开那张结账单的明细（订单查询的同一个抽屉 `OrderDrawer`：逐行明细、收款、退款单）。看明细要「查看当日流水」，历史营业日的要「看历史流水」（与订单查询同一个口径），没有的只显示单号。收银台「结账记录」本来就能点开明细，不动。

## 8. 同行快捷移出

- 原来：「更多 → 退出同行组」只能把当前打开的牌退出。
- 做法：客人卡同行一栏的每个在店同行小标签上加「移出」，确认一下就把那张牌移出同行组（`POST /api/frontdesk/visits/:mateId/group {action:'leave'}`，原来的接口与锁，不另写），之后刷新当前这张牌。只改同行关系，已挂的明细留在原牌上。

## 9. 全店补单（纪要「补单：需要全店下单台权限，可补录餐饮、项目消费」「退单：作废需备注」）

- 原来：补录纸质单（`frontdesk.backfill`，值班经理及以上、48 小时内）能补接待、挂账、结账，要纸质单号；没有出单员。
- 做法（复用补录）：新权限「补单」（`frontdesk.supplement`，默认值班经理及以上）。收银台顶上「补单」打开补单条：实际时间、出单员（在职员工）、单号（选填，没填记 `BD-月日-时分`）。之后收银台「加项目」按这个时间与出单员挂到在店客人的手牌上：
  - 请求还是原来的挂账接口，`backfill` 多带 `issuerId`（不带时与以前完全一样）；服务端 `resolveBackfill` 认出是补单，只许挂账，接待、结账带补单回 `SUPPLEMENT_ONLY_CHARGES`。
  - 时间规则与补录相同（48 小时内、不晚于现在、不早于接待）；餐饮的菜直接记「已上」、不进厨房屏、不打厨房单、不扣今天的沽清（补录本来的做法）；扣料照补录。
  - 出单员记在 `bill_supplements`（操作编号 = 明细的 `post_key`），明细上写「补单 · 出单员 某某，某某录入」，日结、对账包的异常清单照旧列为补录。
  - 作废照常（写原因、经办人）。

## 11. 没做的（要店主确认或不在这一批）

- 门票套餐叠加（纪要「未来可能有 20 多种门票叠加」、8 小时门票的结算逻辑）：要店主给真实套餐与叠加规则，这一批不做。
- 男女宾、水吧、餐厅「单独做下单功能」（下单点）：纪要只说「需要」，没定是新的终端还是现有点单页按出品口分，留给店主定。
- 快捷键、单项打折、押金、明细经办人显示、换牌规则：在另一批（批 1）做。
- 同行人批量发 5 张牌：纪要写「因芯片未到，暂无法批量」，等芯片。
- 会员充值的权限归属：纪要写「待定，需看康总那边怎么定」。
- 高风险推送到企业微信、手机：用现有的站内通知；企业微信等外发通道登记了就跟着发，这一批不另接。

## 12. 接口与数据一览

- 新接口：`GET/PUT /api/frontdesk/guest-rules`、`POST /api/frontdesk/visits/:id/category`、`PUT /api/frontdesk/visits/:id/preferences`、`GET /api/frontdesk/guest-notes`、`GET /api/frontdesk/complaints`、`POST /api/frontdesk/complaints/:id/resolve`、`GET /api/frontdesk/risk-alerts`、`GET /api/frontdesk/supplement/issuers`。
- 改的接口：发牌每位客人多 `category`、`bookedTechnician`（选填，不带时摘要不变）；挂账的 `backfill` 多 `issuerId`（补单）；手牌板 `visit.guestCategory`；来访详情 `guest`（类别与偏好）、经办记录多 `guest` 一类；余额变动 `checkoutId`；预约各接口按种类核对权限。
- 新表：`visit_category_changes`、`guest_preferences`、`visit_remark_resolutions`、`visit_risk_alerts`、`bill_supplements`；新列 `visits.guest_category`。数据字典已重新生成。
- 设置：`frontdesk_guest_rules`（按店）。
- 用例：`tests/frontdesk-v8223.test.ts`（九条各一组），`tests/position-catalog.test.ts`（建议权限与配置日志）。
