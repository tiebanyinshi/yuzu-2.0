## 2. 数据模型（迁移 `230_price_catalog.sql`）

- `price_catalog_sets`：一份价目表（导入的一份文件，或手工维护的一份）。`status`：草稿 `draft` / 生效 `active` / 停用 `retired`；一家门店同时最多一份草稿、一份生效。导入先落草稿；核对条数无误后再切换生效（第 5 节），原来生效的那份转停用，可以整体回滚到它。
- `price_catalog_entries`：价目表里的一项。
  - **价格形态** `price_mode`：
    - 双价 `dual`：专业价 `price_cents` + 资深价 `price2_cents`。
    - 单价 `single`：只有 `price_cents`。
    - 无价格 `none`：待定价或免费，两个价格都是**空值**、不存 0；页面写「待定价」，不写「0 元」。
    - 比例 `rate`：服务费 `rate_bp`，万分之几，10% = 1000，不在商品上存 0.1 元。
    - 数据库约束保证形态与价格列一致。
  - **金额**：一律整数分。「399/2H」「加钟/19.9」「688 元/位」这类写法拆成价格、时长、单位分别存：
    - 时长：`duration_minutes`，一律分钟——按摩服务时长、门票 12H / 24H、娱乐与房间的「基础价含几分钟」。
    - 加钟价（娱乐）/ 超时单价（房间）：`extra_price_cents`，加上每次多少分钟 `extra_minutes`。
    - 封顶价：`cap_cents`。
    - 台位数 / 房型总间数：`units_count`。
    - 房号清单：`room_numbers`。
    - 时段：`window_start` / `window_end`，0–1439 分钟，跨零点时结束小于开始。
    - 是否含餐：`includes_meal`。
    - 适用房型：`venues`，房间 / 大堂 / 浴区。
    - 适用性别：`gender`。
    - 核心人群、操作内容、项目亮点、备注。
  - **一项里还分档的** 放在 `variants`，每档有名称、价格、分钟、单位、房号、几人位：
    - 轰趴房按面积分 4 档，每档 6 小时 / 12 小时 / 包天；
    - 客房大房间、小房间的过夜价与 3 小时价；
    - 餐饮包房的三种位价与低消；
    - 棋牌房的 8H 价。
  - **板块 / 餐段**存在 `section`，**菜品分类**存在 `category`，**原始编号**存在 `code`，**表格行号**存在 `source_row`，便于与表格核对。
  - **不录内部参考字段**：成本、成本率、思路、核心定位都不录（需求说明第五节）。
  - **停用不删除**：停用是把 `active` 改成 false，不物理删除。
  - **能不能下单**：`orderable`。2 楼零点没有售价的菜录为「待定价」、不能下单，补价后启用（约束：菜品无价格时不能可下单）。

## 3. 导入（第一批）

- `GET /api/admin/price-catalog/template`：导入模板，与《价目表 1119》同结构的六张表（表头照原表，数据留空）。
- `POST /api/admin/price-catalog/import/preview`：读 `.xlsx`，六张表按工作表名认，逐行校验，返回：
  - 条目；
  - 问题：写明工作表、行号、字段与原因。`error` 挡导入，`warning` 只提醒；
  - 条数对照；
  - 预览摘要。
- `POST /api/admin/price-catalog/import`：带预览摘要与操作编号 `opKey`（页面每次预览配一个；迁移 `232`）。结果不确定原样重提时返回第一次导入的那份草稿；那份草稿后来已被替换或放弃的拒绝（`IMPORT_DONE`），同一编号换了文件的拒绝（`IMPORT_OP_REUSED`）。页面每次导入用新的编号，提交前把编号与原请求（含文件内容）存在本机并读回核对，存不了就不发；结果不确定（断网、超时、服务器出错）时页面上方列出这一笔，只能查回、按原内容重新提交或确认作废（`/api/erp/ops`，类型 `price_import`；作废登记在 `op_fences`，迁移 `234`），在此之前不能再导别的文件。文件与预览时不一样的拒绝（`IMPORT_STALE`），有 `error` 的整份不导（`IMPORT_INVALID`）。导入成这家门店的草稿，替换原来的草稿（门店级咨询锁 → 原草稿行，再删、再写；`docs/LOCKING.md`），留审计（`price_catalog`，`detail.action = import`）。
- `GET /api/admin/price-catalog`：生效与草稿两份的概要与条数对照。`GET /api/admin/price-catalog/sets/:id`：一份价目表的全部条目。
- 权限沿用「管理充值套餐与消费项目」（`catalog.manage`；需求说明：不改权限模型）。

挡导入的问题：
- 表头少了某一列或写错字（「资深价格」「核心针对人」）：每张表读到的列都要有（按摩及助浴还有核心针对人群、服务操作内容、项目亮点），写明少了哪一列（不然整列成了空的，双价悄悄变单价、说明悄悄清空）；
- 导入的每一项最后再用页面编辑的同一份校验过一遍（分档 0 小时之类），导进来的都能照常修改；

- 文件本身不对：合并区域过大（一个超过 2000 格或一张表合计超过 5 万格）、一张表超过 2000 行、一个房型合并超过 20 行，整份拒绝（`IMPORT_FILE_INVALID`）；
- 少了某张表、表头不对（零点菜品每个餐段的表头要有「菜品分类」「菜品名称」「售价」，写错字的报出是哪一行、少了哪一列）；
- 房号过多（一个房型超过 300 个）；
- 房间分档、超时价、封顶价写了金额却不合法（「6小时：0」「包天：0」「0封顶」「超时0/H」）：报错，不当成没填、没有封顶；
- 价格为空（零点菜品除外，菜品没写售价是「待定价」）、价格写法看不懂、金额多于两位小数（「599.999/晚」整段报错，不截出其中一段）；
- 时长格式不支持或不在 1–2880 分钟里（娱乐价格「39/0min」也算），时段看不懂（时、分各自要合法，「7:99」不换算成 8:39）；加钟价多出来的位数（「加钟/19.999」不截成 19.99）；
- 名称重复：每张表都查——同一张表、同一个板块 / 餐段、同一个分类里（不分大小写、不管空格，与页面编辑同一个查重键），写明第一次出现在第几行；
- 板块不存在、餐段不认识。

只提醒的：

- 菜品待定价；
- 表格自相矛盾，请门店核对：
  - 房型的总间数与房号清单算出来的个数对不上（原表 SPA 房写 35 间、S301–S339 是 39 个；按摩房 30 间、M301–M329 是 29 个；足浴情侣房 6 间、F301–307 是 7 个；客房 7 间、R01–R08 是 8 个；轰趴房 9 间、H201–H210 是 10 个）；
  - 轰趴房 100 平、150 平的 12 小时价比 6 小时价低。

## 5. 编辑与校验（第三批，迁移 `231_price_catalog_edits.sql`）

同一页（`PriceCatalogPane.tsx`，表单与改动记录在 `PriceEntryDialog.tsx`；服务端 `src/server/modules/price-catalog/edit.ts`）：

- **单条新增**：「条目」右上角「新增一项」，选工作表与种类（服务费只有一条规则，不新增），排在这张表最后。
- **修改 / 改价**：每行「改」。价格形态在单价 / 专业·资深 / 待定价之间切换；待定价两个价格都空着（不存 0），服务费按百分比填。分档（轰趴房各面积、客房大小房、餐饮包房位价……）能改价格，档名与档数照导入的表（PC13）；主价格由分档推出来的（轰趴房 = 各档最低价、餐饮包房 = 位价里最低的、客房 = 过夜价里最低的，与导入同一个口径）跟着分档变，页面上不另填。
- **停用 / 启用**：停用不删除（写原因），历史单据照旧显示名称与价格；停用的不算条数。启用时同名在用的挡下。
- **校验**（页面边填边提示、服务端写入前再查一遍，同一份 `priceEntryProblems`）：价格形态与价格一致；金额大于 0、不超过 100 万元；待定价不填价格；只有服务费按比例；待定价的菜不能下单；按摩板块必须是 9 个之一、零点餐段必须是 4 个之一；时长、时段、台位合法；填了每次分钟就要填加钟 / 超时价。名称重复（同一张表、同一个板块 / 餐段、同一个分类里在用的，不分大小写、不管空格）在服务端锁里查（`PRICE_NAME_DUPLICATE`）。
- **改价留痕**（`price_catalog_changes`，只追加）：新增、修改、停用、启用各一条——经办人、时间、改前与改后的整项、原因、价格有没有变（`price_changed`）。页面「改动记录」按「标签：旧 → 新」列出改了什么（价格那行在最前，如「价格：专业 ¥499.00 / 资深 ¥599.00 → 专业 ¥529.00 / 资深 ¥599.00」），可以只看改价；每行「记录」看这一项的全部改动。
- **版本号**：修改、停用带着读到的版本号，别人先改过就拒绝（`PRICE_VERSION`），刷新后再改；什么都没改的保存不留痕、版本不变。
- **操作编号与「结果待确认」**（迁移 `235`）：新增、修改、停用 / 启用都带操作编号，编号记在那一条改动留痕上（`price_catalog_changes.op_key`）。页面提交前把编号与原请求存在本机，结果不确定（断网、超时、服务器出错）时在页面上方查回、按原内容重新提交或确认作废（类型 `price_entry`）；原样重提返回这一项现在的样子、不再写一次；作废过的原请求晚到也不改。确认之前「新增一项」「改」「停用」都不能点。
- **一键切换生效**：草稿上「切换生效」。条数与表格（224 项、每个板块 / 餐段）一致的直接切；对不上的列出差几项，写明原因才切（PC11，原因记进审计）。原来生效的那份转停用，成为「上一版」。
- **整体回滚**：生效中的那份上「回滚到上一版」，写原因；上一版恢复生效，刚才那份成为上一版（PC12）。带操作编号（迁移 `233`）：结果不确定原样重提时什么都不改，不会把之后别人切换的结果再切回去；页面同样先存本机，结果不确定的在页面上方查回、重提或确认作废（类型 `price_rollback`）。
- **放弃草稿**：草稿连同条目、改动记录一起删掉，审计留一条（PC14）。
- 切换生效、放弃草稿与整体回滚一样带操作编号（迁移 `236`，记在 `price_catalog_set_ops`）：原样重提什么都不改、返回现在的样子；页面先存本机，结果不确定时查回、重提或确认作废（类型 `price_set`），确认之前这几个按钮都不显示。
- 生效中的价目表也能直接改，改了马上作数（PC9，第四批起开单取它）；换下来的旧版不能改（`PRICE_SET_RETIRED`）。
- 接口（权限都是 `catalog.manage`）：`POST /api/admin/price-catalog/sets/:id/entries` 新增，`POST /api/admin/price-catalog/entries/:id` 修改，`POST /api/admin/price-catalog/entries/:id/active` 停用 / 启用，`GET /api/admin/price-catalog/sets/:id/changes`（`?entryId=`、`?priceOnly=1`）改动记录，`POST /api/admin/price-catalog/activate`（`draftId`、对不上时 `countReason`），`POST /api/admin/price-catalog/rollback`（`activeId`、`reason`），`POST /api/admin/price-catalog/discard`（`draftId`）。概要（`GET /api/admin/price-catalog`）多了上一版 `previous`。
- 审计（`price_catalog`）：`entry_create` / `entry_update` / `entry_deactivate` / `entry_reactivate` / `activate` / `rollback` / `discard`，审计记录里写成「草稿修改「古法中式」（改价）」「切换生效「…」」这样的一句。
