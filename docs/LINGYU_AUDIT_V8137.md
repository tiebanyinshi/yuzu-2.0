## 3. 没做、为什么

- **反结账后客人回店接着消费**：反结账恢复在店时门票计到第一次结账的时刻，这是数据库触发器（迁移 017）守着的规则——反结账是「更正」，客人已经走了。客人真的回来，按新来访开牌。
- **问题表里的新需求**（结账单印券号、券限星期 / 时段 / 门店、点钟券、发券试算、房号从大到小排、过夜筛选、排位调到某人前面、一次派多张手牌、加钟换项目后看板的项目名）：不是缺陷，等店主排优先级。

## 4. 对照结论（已经防住、或我们没有这个功能的）

- 券：同一张券不能重复核销（锁券、状态触发器、只追加的使用记录），用了在同一个事务里扣掉；代金券只抵适用范围；反结账券退回。
- 重复提交：结账、挂账、开卡、充值、扫码点餐都带操作编号，重提返回第一次的结果。
- 预结账跳差价：预结账只是只读汇总，结账时在同一个事务里重算，与员工确认的不一致就拒绝；预结后照样能减免。
- 余额：数据库约束不能为负；退储值只退本金余额以内、要店主或店总当场授权。
- 绑卡：要微信验证过的手机号等于会员档案上的手机号；一个微信一位会员、一位会员一个有效绑定（唯一索引）。
- 扫码点餐：要在店手牌、桌码带签名，人不在店点不了。
- 钟房派钟：按门店的技师队列锁、一位技师同时只有一张上钟中的钟单（唯一索引）；换技师排除原技师、只能换给能做的；休假按营业日。
- 不涉及（我们没有）：畅玩券与区域闸机、技师 App、自动退房、按比例的服务费、小费。

## 5. 接口变化

- `POST /api/frontdesk/checkouts`：多一个可选的 `confirmUnstarted`（钟单号数组）。
- `POST /api/usages`、`POST /api/room-center/rooms/:id/usage`、`POST /api/rooms/checkin`：多一个可选的 `useReserved`。
- `POST /api/auth/authorize`（`over_limit`）：范围多一个可选的 `manual`（手动金额合计）。
- `GET /api/frontdesk/technicians`：每位技师多 `queue`（今天的上牌状态、在不在钟上、排第几）。
- `GET /api/audit`：多 `actions`（`sensitive` 或逗号分隔的动作名），`limit` 最多 2000；新 `GET /api/audit.csv`。
- `GET /api/dining/ledger`、`/export`、`/api/dining/voids`：权限从「餐饮点单」改为「餐饮台账」（或看日结、经营报表）。
- 新的拒绝码：`SESSION_REGISTERED`、`SESSIONS_NOT_STARTED`、`SPACE_BOOKED`、`ROOM_TYPE_RESERVED`；前台轮钟可能返回 `TECHNICIAN_OFF`、`TECHNICIAN_RESTING`、`TECHNICIAN_BUSY`、`SKIP_REASON_REQUIRED`。
