# 柜况与智能柜锁接口（8.1.49；第 6 节 M1 手牌发卡器，店主 2026-11-27）

店主 2026-11-26：「目前系统里有查看锁柜的功能吗？没有请帮我加上……看看智能硬件列表有没有锁柜的信息，提前做好对应接口。」

## 1. 原来有什么、缺什么

- **手牌就是柜子的钥匙**：一牌一柜，柜号就是牌号（全店 747 个，编码规则见 `docs/PENDING_DECISIONS.md` 附录 A）。系统里没有单独的「柜子」，柜子 = 手牌（`hand_tags`）。
- 原来能看到柜子的地方：
  - **发卡台**的手牌板：用来发牌，所有空闲柜子都列成小标签；
  - **后台「手牌」**：管理表格，用来建牌、停用、改柜型、维修。
- **缺的**：
  - 一个只看不操作、按区汇总的「柜况」：值班经理想知道哪个区还剩几个空柜、哪些锁着或在修，原来只能在发卡台一个个数；
  - 柜锁硬件的接口。
- **智能硬件清单里没有柜锁**：`docs/HARDWARE.md` 与 `docs/PENDING_DECISIONS.md`（D8）都写着「采购清单缺门锁客控、手牌柜锁控、闸机，本期不做；要做时另行采购」。所以柜锁这次只做接口：
  - 控制器到货前，系统照常用；
  - 到货后按第 3 节配置即可，不用再改业务代码。

## 2. 柜况页（门店 → 前台 → 柜况，`/crm/lockers`）

- **谁能看**：能看在店手牌的（`frontdesk.read`），和发卡台、收银台一样。
- **数据**：就是发卡台的手牌板（`/api/frontdesk/board`），每 10 秒刷新，不另建表、不另写查询。
- **顶部汇总**：共几个柜，各状态几个。各状态是：
  - 在用：有客人；
  - 锁定：前台锁的牌；
  - 维修中、暂停使用：后台「手牌」里标的；
  - 停用；
  - 空闲。
- **分组**：
  - 普通柜按「男宾 / 女宾 × 区号」分组（如「男宾普通柜 A 区」）；
  - VIP 柜按等级分组（如「男宾 VIP 第 3 级」）；
  - 每组写几个、在用几个、空闲几个、不可用几个。
- **筛选**：可以按状态筛，比如只看空闲的。
- **状态判断**：有客人的一律算「在用」，即使这个柜子同时被锁定或标了维修。
- **点一个柜子**：看这个柜子的详情：
  - 在用的：谁在用、来访单、入场时间、同行组；
  - 锁定的：锁定原因；
  - 维修或暂停的：说明。
- **柜况页只看**：发牌、换牌、锁牌照旧在发卡台做。

## 3. 智能柜锁接口（预留）

各厂家的柜锁控制板协议不同：有的走 RS485 串口，有的走厂家云。门店系统**不认具体厂家**，只认一个「柜锁桥」。柜锁桥是装在门店机上的小程序，由厂家或我们按厂家协议写，负责把厂家协议翻译成下面两个接口。

**环境变量**（`.env`）：

| 变量                  | 说明                                                                                   |
| --------------------- | -------------------------------------------------------------------------------------- |
| `LOCKER_DRIVER`       | `none`（默认：没接；不显示开柜按钮）、`mock`（模拟：开发、测试用）、`http`（接柜锁桥） |
| `LOCKER_BRIDGE_URL`   | `http` 时必填：柜锁桥的地址，如 `http://127.0.0.1:9300`                                |
| `LOCKER_BRIDGE_TOKEN` | `http` 时必填：至少 32 个字符。门店系统调桥时带 `Authorization: Bearer <它>`，桥要核对 |

配错了（driver 写错、`http` 没给地址或密钥太短）应用不启动，日志里写原因。

**柜锁桥要提供的两个接口**：两个都是 JSON 接口，门店系统每次等 5 秒。

| 接口          | 请求                              | 回答                                                                                                                                                                         |
| ------------- | --------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /open`  | `{ "code": "A8060" }`             | `{ "ok": true, "message": "3 号板第 7 路" }`；没开成：`ok: false`，`message` 写原因                                                                                          |
| `POST /doors` | `{ "codes": ["A8060", "A8061"] }` | `{ "doors": [{ "code": "A8060", "doorOpen": false, "known": true }] }`。控制器查不了门状态的，`doorOpen` 给 `null`；桥的编号表里没有的柜号，`known` 给 `false`，或干脆不返回 |

柜号就用手牌号。桥里维护「柜号 → 控制板地址 / 第几路」的对照表。

**门店系统的接口**：

| 接口                          | 权限                         | 说明                                                                                                                                                      |
| ----------------------------- | ---------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /api/lockers/controller` | 查看在店手牌                 | 接的是哪种控制器、能不能远程开柜，以及常用的开柜原因                                                                                                      |
| `POST /api/lockers/doors`     | 查看在店手牌                 | 问控制器这几个柜门开着没有，一次最多 1000 个。没接控制器时返回空；控制器没回应时回 502 `LOCKER_CONTROLLER_DOWN`                                           |
| `POST /api/lockers/:id/open`  | 维护手牌池（店长、值班经理） | 远程开柜，要写原因（2–100 字）。开成、没开成都记审计（`locker_opened`，含柜号、原因、控制器、结果）。没接控制器时回 503 `LOCKER_NOT_CONFIGURED`，不记审计 |

**开柜规则**：

- 开柜在数据库事务外进行，不会拿着数据库连接等控制器。
- 不自动重试：开两次没坏处，但要让人知道第一次没开成，页面会提示原因。
- 柜子里有客人时，页面要求确认「是客人本人要开」，按钮显示成危险操作。

**页面**：

- 接了控制器、且有「维护手牌池」权限的人，点柜子时多一个「远程开柜」，要写原因。快捷原因有：客人忘带手牌、手牌失灵、清洁检修、客人遗留物品。
- 没接控制器时，有这个权限的人在柜况页上会看到一行提示「还没有接智能柜锁控制器」。

## 4. 以后

控制器到货后，按下面的顺序接入：

1. 按厂家协议写柜锁桥，先用 `curl` 对着第 3 节的两个接口试；
2. 门店机 `.env` 配 `LOCKER_DRIVER=http`、地址和密钥，重启应用；
3. 柜况页点一个空柜，远程开柜试一次；后台审计里能看到这次开柜。

两项还要店主定：

- 要不要在柜况上显示柜门开着没有：要调 `/doors`，按每 10 秒查全店 747 个柜计算，看控制器扛不扛得住；
- 发牌时要不要自动开柜。

## 6. M1 手牌的发卡器（店主 2026-11-27：泰格柜锁）

店主 2026-11-27 发来门店柜锁的照片（衣物柜、手机柜同一种锁）：「你能查到这家智能锁硬件公司使用的接口协议吗？提前做好协议接通。」「手牌是 M1 芯片。」

### 6.1 查到的情况

- **厂家**：锁上标「沈阳泰格 荣誉出品」「TAIGE · SERVES THE WHOLE WORLD」、热线 400-004-8158，对应沈阳泰格科技发展有限公司（官网写着做桑拿、洗浴、汗蒸的电子更衣柜锁）。
- **接口协议没有公开**：公开网页、开发者社区都查不到泰格柜锁、发卡器的接口文档或 SDK；官网在这次会话里也打不开。同类厂家（酒店门锁、洗浴柜锁）的做法都是：收银软件调厂家给的发卡器动态库（Windows 的 DLL），写卡的扇区、密钥由厂家定，不对外公开。没有厂家的库，第三方写出来的卡开不了锁。
- **所以要向厂家要的**（拨 400-004-8158 或找安装的经销商）：
  1. 锁和发卡器的型号；锁是**单机电池锁**还是**联网锁**（RS485、网口、云）；
  2. 手牌（M1）的用法：**固定柜**（一牌一柜，牌出厂就写好了柜号）还是**自选柜**（每次发牌在发卡器上写柜号）；衣物柜、手机柜是不是同一张牌都能开、手机柜怎么编号；
  3. 「第三方收银 / 洗浴管理软件对接」的接口：发卡器动态库（函数说明、调用示例）或者联网锁的通讯协议，读卡、写卡、清卡（退牌）、挂失怎么调；
  4. 发卡器的连接方式（USB、串口）、要装的驱动；
  5. 丢了手牌怎么让旧牌开不了锁（挂失卡、管理卡、换锁芯）。

### 6.2 这次做的：柜锁桥加三个发卡器接口

门店系统照旧不认具体厂家。泰格这类单机锁开不了远程，但前台有发卡器；所以柜锁桥（第 3 节）除了开柜、查柜门，再加三个发卡器接口。拿到厂家的库以后，在前台电脑上写一个柜锁桥调厂家的 DLL，把这三个接口接上就行，门店系统不用再改。

**能力开关** `LOCKER_CAPABILITIES`（`.env`，逗号分隔）：`open`（远程开柜）、`doors`（查柜门）、`card`（发卡器）。`http` 默认 `open,doors`（与以前一样）；泰格单机锁配 `card`；`mock` 三样都有。写了不认识的、`http` 一样都没写的，应用不启动。

**柜锁桥再提供的三个接口**（JSON，带同一个 `Authorization: Bearer`，每次等 5 秒）：

| 接口               | 请求                                     | 回答                                                                                                                                                                                                                                                     |
| ------------------ | ---------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /card/read`  | `{}`                                     | 读发卡器上放着的卡：`{ "ok": true, "uid": "04A1B2C3", "code": "A8060", "locks": [{ "kind": "clothes", "no": "A8060" }, { "kind": "phone", "no": "P060" }] }`。空白卡 `code` 给 `null`、`locks` 给 `[]`；没放卡、读不出来：`ok: false`，`message` 写原因  |
| `POST /card/write` | `{ "code": "A8060", "uid": "04A1B2C3" }` | 把发卡器上的卡写成能开这个手牌号的柜（衣物柜、手机柜都写，**手牌号 → 哪几把锁由桥里的对照表定**）：`{ "ok": true, "uid": "04A1B2C3", "message": "已写：衣物柜 A8060、手机柜 P060" }`。带了 `uid` 而发卡器上是另一张卡的，不写、`ok: false`（防止写错卡） |
| `POST /card/clear` | `{ "uid": "04A1B2C3" }`                  | 把发卡器上的卡清成空白（退牌回收、作废）：`{ "ok": true, "uid": "…" }`；`uid` 的用法同上                                                                                                                                                                 |

`locks[].kind`：`clothes` 衣物柜、`phone` 手机柜、`other` 其他（鞋柜等）。`uid` 就是 M1 芯片的卡号（与后台「手牌」里绑的芯片号同一种写法：去掉分隔符、转大写）。

**门店系统的接口**（都在数据库事务外调桥）：

| 接口                               | 权限         | 说明                                                                                                                                                                                                   |
| ---------------------------------- | ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `POST /api/lockers/card/read`      | 查看在店手牌 | 读发卡器上的卡；再按芯片号找它绑的是哪张手牌（`hand_tags.card_uid`），卡里写的柜号与绑的手牌对不上的标出来。只读、不记审计                                                                             |
| `POST /api/lockers/:id/card/write` | 维护手牌池   | 把发卡器上的卡写成这张手牌的柜（补发手牌、手牌失灵重写），要写原因；写成、没写成都记审计 `locker_card_written`（柜号、芯片号、原因、结果）。写好以后芯片号还没绑这张手牌的，页面提示去绑（不自动改绑） |
| `POST /api/lockers/card/clear`     | 维护手牌池   | 清卡（退牌回收、作废），要写原因；记审计 `locker_card_cleared`                                                                                                                                         |

没配发卡器（能力里没有 `card`）回 503 `LOCKER_CARD_NOT_CONFIGURED`；桥连不上、没回应回 502 `LOCKER_CONTROLLER_DOWN`。写卡、清卡都不自动重试：重写同一张卡没坏处，但要让人知道上一次没成。

**结果待确认**（Codex 审查 f8b2853）：桥回 4xx 算明确没做；超时、断线、5xx、回的不是 JSON 算「没收到回答」——桥可能已经写了、清了、开了：

- 写卡、清卡：读回一次发卡器上的卡，已经是要的样子（写成了那个柜、清成了空白）就按做成算，回话里注明是读回核对的；对不上或读不到的，回 `ok: false, uncertain: true`，审计里也记 `uncertain`，页面提示「结果待确认：点『读卡』核对；没写成再写一次」，不说没写成；
- 远程开柜：能查柜门的查一次，开着就按开了算；否则 `uncertain: true`，提示到柜前确认。

**模拟柜锁桥用公共 HTTP 底座**（`lib/http-kit.ts`）：请求编号、日志脱敏、统一的错误出口、服务密钥比对，与门店主程序同一份。

**页面**：柜况页顶上多一块「发卡器」（配了 `card` 才有）：「读卡」看卡号、能开哪几把锁、绑的是哪张手牌；有「维护手牌池」权限的多「清卡」。点一个柜子多「写卡」（写原因；柜子里有客人的要确认，按钮显示成危险操作）。

**模拟柜锁桥**：`node dist/server/cli.js locker-bridge-mock [--port 9300] [--token …]`，按本节与第 3 节的五个接口回话，命令行里 `card 04A1B2C3` 放一张卡、`remove` 拿走、`show` 看现在的卡。写泰格的桥之前、或者厂家来对接时，先拿它把门店系统这头试通。

### 6.3 还没做、等厂家资料再定

- **发牌、退牌自动写卡、清卡**：固定柜（一牌一柜，牌早就写好了）不用；自选柜要在发牌时写、退牌时清。看厂家答复再接进发卡台（`docs/PENDING_DECISIONS.md` GK3）。
- **挂失**：单机锁要靠厂家的挂失卡或管理卡，系统里先照旧「换牌 + 锁定原手牌」（GK4）。
- **泰格的柜锁桥本身**：要厂家的 DLL 与说明才能写；拿到以后按 6.2 的接口写，跑在前台装发卡器的那台 Windows 电脑上。
