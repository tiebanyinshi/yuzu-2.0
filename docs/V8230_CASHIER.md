## 1. 港元现金（CM-2、CM-3）与大额找零（CM-4）

- **开关与汇率**：后台「手牌与前台 → 收银台」设「每 1 港元折多少人民币」（`frontdesk_rules.hkdRatePpm`，百万分之一，0.5–1.5 之间）；没设 = 不收港元（默认）。
- **收法**：结账时「现金」那一笔切到「港元」，填客人实给的港元。这笔的金额照旧是人民币（应收的一部分），页面显示「这笔折 HK$x」（人民币按汇率向上取到港仙）；实给的港元按汇率向下折成人民币，不能少于这笔，多出来的**找人民币**。
- **记什么**：`checkout_payments` 照旧记一笔 `cash`、人民币金额；另记币种、实给的港元、汇率快照、折成的人民币（= 金额 + 找零）、找的人民币（`fx_*`，约束保证 `fx_worth = amount + fx_change`）。以后改汇率不影响已结的单。
- **核对**：只有现金能带港元；提交的汇率要等于门店此刻的汇率（改过了拒绝 `HKD_RATE_CHANGED`，页面重新核对）；折成的人民币不够拒绝 `HKD_SHORT`。
- **营业额、日结、对账包、看板**：都按人民币（金额本来就是人民币），不用改。
- **交班**：港元进钱箱、找零从人民币出，所以结账现金里这几笔折成的人民币（收款 + 找零）从应有现金扣掉（`cash.hkd`），另列应有港元（= 实给的港元合计）。收过港元的班次交班时要填实点港元，带上看到的应有港元（交班期间又收了港元拒绝 `SHIFT_CHANGED`），记进 `shifts.expected_hkd`、`counted_hkd`；交班表与打印的交班表都列出来。
- **退款、反结账**：港元收的按人民币退（退款单、反结账退的是这笔的人民币金额，从钱箱的人民币出）。
- **大额找零**（页面）：现金填了客人实给、找零超过门槛（后台改，默认 ¥500）或超过这笔的 2 倍时，要再按一次「确认结清」（防止 100 输成 1000）。港元的找零按汇率折人民币同样算。合并 main 时 8.2.27 已有「找零大再按一次」，原来的「已核对找零」勾选去掉，两处合成一处（PR 的合并条件：main 做过的就瘦身）。

## 2. 收银申请（CM-5、CM-6）

没有「开退款单」「反结账」权限的收银员不再办不了：

- **提交**：结账记录里「申请部分退款」（同一个退款区，填项目、份数、金额、方式与原因，不选钱箱、不填怎么退；请求里带了钱箱、原路退回、退款单号也丢掉不存）或「申请反结账」（写原因）。写一行 `cashier_requests`（只追加），操作编号幂等（`cashier_request`，「结果待确认」照旧）。推站内通知给这家店有对应权限的人（`approval_todo`）。
- **一张结账单一张**：同一张结账单同时只能有一张待审批（唯一索引）；有待审批的申请时，有权限的人也不能直接开退款单、反结账（`REQUEST_PENDING`），要先批准或驳回。
- **批准**：在「收银申请」页（`/crm/cashier-requests`，通知点进来）点「批准」，**走原来的开退款单 / 反结账**（同一个函数、同一套核对与加锁顺序），在同一个事务的最后锁住申请一行、记批准。批准照「结果待确认」：批准人的页面提交前把操作编号与原请求存进本机，超时、断网、服务器出错留着查回 / 原样重提 / 确认作废（见第 6 节）。现金默认从批准人当班的钱箱退（批准人要开班）；接口也能带批准人选的钱箱，只能是这家店此刻当班的。不能批自己的。
- **单子变了**：批准时按此刻的数据核对，已反结账、已退过、项目或方式超额的（`STALE_CODES`）把申请记「已失效」、写明原因并通知申请人；批准人这边的问题（没开班、超过时限）申请留着。
- **驳回**要写原因，通知申请人（`approval_result`）；申请人可以撤回自己的。
- **超时**：24 小时没人处理，每分钟的扫描记「已失效」并通知申请人。
- 为什么不接审批中心（`modules/approvals`）：那套的审批级次、岗位组按 ERP 的权限算，收银的批准就是「有开退款单 / 反结账权限的人」，单独一张表更直、执行时直接复用原来的函数。

## 3. 交班盲点与交接清单（CM-9）

- **盲点**：后台开「交班盲点」（`shiftBlind`，默认关）。开了以后交班页先只填实点（与实点港元），点「提交实点」交给服务端记下（`shift_blind_counts`，只能一次），之后才显示应有现金、差额与交班汇总，再确认交班（实点要与提交的一致）。提交之前班次的接口（交班页、「今天的班次」、打印预览、打到小票机）都不给当班的人金额，见第 6 节。
- **交给下一班**：交班页列出本人提交、没人批的申请，等本人审批的申请数，没读的通知数，此刻在店没结的手牌数。只是提醒，不拦交班。

## 4. 餐饮补全（CM-16 到 CM-21，迁移 `761`）

- **等叫、加急、打包（CM-16）**：点单页「还没上的菜」与桌台明细里，一道或整单（「整单等叫 / 起菜」）标记（`POST /api/dining/items/flags`，按 id 升序锁住这几道）。等叫只能标在还没开始做的；等叫着厨房屏的「开始做」「出餐」点不了（服务端拒绝 `DISH_HELD`），服务员点「起菜」以后照常。加急、打包只是标记，厨房屏、明细上带出来，不动金额。记审计。下单当时还不能直接标，下完马上在「还没上的菜」里标。
- **沽清一键恢复（CM-17）**：沽清页「全部恢复」把今天的沽清、限量一起取消（与下单扣沽清同一个顺序先锁再删），记审计。柚子的沽清本来按营业日记、换了营业日自动不算，这一点照旧（原型「第二天不自动恢复」不采用，免得改了门店已经习惯的用法）。
- **待催（CM-18）**：桌台看板带最早一道下了单、还没出餐的菜的下单时刻（等叫的不算），超过餐饮规则里的「多少分钟没出餐标红」在格子上标「待催 N 分钟」。用柚子已有的这一个分钟数，不另设餐厅 / 奶茶两个（原型的 20 / 10 分钟可以按店改这一个数）。
- **分次上菜（CM-19）**：出餐以后一行几份可以先上 1 份（`served_qty`），上齐了才算已上菜；撤回先撤上的份数。退菜照原来的权限与留痕。
- **吧台杯型、温度、糖度、小料（CM-20）**：不做。8.1.17 的做法分组（一组只能选一个、能设必选、能加价，`docs/DISHES_V8117.md` 第 2 节）与加料已经能做：杯型、温度、糖度设成必选的组，小料设成加料。8.2.19 水吧（首杯免费、取餐号）照旧。
- **杯贴（CM-21）**：厨房屏上水吧的出品单多「杯贴」，打开打印页（`/print/cup-labels/<出品单号>`），一单的饮品一杯一张：取餐号（8.2.19 的，有的话）、品名、做法与备注、第几杯、手牌或桌号、时刻。浏览器打印，贴纸打印机当普通打印机用；要接专门的标签机指令以后再说（真机确认）。

## 6. Codex 审查修正（06b2eee）

- **批准是收款，照「结果待确认」**（P1）：「收银申请」页的批准改用前台的待确认记录（`useFrontdeskOp`）：提交前存下编号与原请求，存不了不发；超时、断网、服务器出错留在卡片上（申请已不在列表里的在页面顶上），刷新页面也在，查回 / 按原内容重新提交 / 确认作废。退款申请的编号就是开退款单的编号（`checkout_refund`，查回退款单、作废要「开退款单」权限）；反结账申请的编号记作 `cashier_void_approve`（迁移 `760` 追加进操作编号与作废登记的约束，ref_id 是那张申请，在反结账同一事务的最后写，处理期间被作废整笔回滚；作废要「反结账」权限）。批准一定要带编号；同一编号重提返回同一个结果，内容（钱箱）变了 `IDEMPOTENCY_CONFLICT`。
- **分次上菜去重**（P2）：「先上 1 份」带上页面看到的已上份数（`servedQty`），在出品单的行锁里核对，对不上 `DISH_CHANGED`（同一个请求到两次只上一份）；分次上菜不带拒绝。与厨房屏原来的 `from` 同一个做法，不另加操作编号。
- **等叫的套餐管到别的档口**（P2）：子项单开始做、出餐先对套餐那一张出品单加 `KEY SHARE` 再锁子项单（`docs/LOCKING.md`），套餐在等叫就拒绝 `DISH_HELD`；厨房屏的子项带上套餐的等叫（`hold`），按钮灰掉、标「等叫」；标等叫时套餐有子项已经开始做了拒绝 `DISH_STARTED`。
- **交班盲点在服务端也管**（P2）：门店开了盲点、班次还开着、还没提交实点时，`/api/shifts/current`、`/api/shifts`、`/api/shifts/:id` 给当班的人的班次标 `blind`，汇总里的金额都记 0（只留笔数、备用金、收过港元的笔数），打到小票机拒绝 `SHIFT_BLIND`；能看历史营业日的岗位（`ledger.readHistory`，默认值班经理及以上，看别人班次的同一项权限）照看。提交实点 `POST /api/shifts/:id/blind-count`（谁能交这个班谁能提交；同样的实点重提照旧返回，改了 `BLIND_COUNTED`）；开了盲点没提交就交班 `BLIND_COUNT_REQUIRED`，交班的实点与提交的不一致 `BLIND_COUNT_MISMATCH`（提交时没收过港元、之后才收的港元照填）。「今天的班次」、打印页看到 `blind` 不显示金额、不打预览。
- **退款申请的钱箱由批准人定**（P2 安全）：提交时请求里的 `refundShiftId` 丢掉不存，批准只用批准人带的钱箱（不带 = 批准人自己当班的班次）；所选钱箱在锁里核对是这家店此刻当班的（`lockRefundShift` 加了门店条件，别家店的与不存在一样，已交班的 `REFUND_SHIFT_CLOSED`）。
- 用例：`tests/cashier-v8230.test.ts`（批准重提同一张退款单、换钱箱冲突、按编号查回；反结账批准重提、冲突、查回、先作废后到的不执行；申请人带的钱箱不存、批准人选的钱箱不存在 / 已交班 / 别家店拒绝、默认记到批准人班次；盲点下店员的三个接口不给金额、经理照看、提交实点前不能交班、提交后不能改、交班要一致），`tests/dining-v8230.test.ts`（分次上菜重提拒绝、不带已上份数拒绝；等叫的套餐子项开始做、出餐拒绝、厨房屏带等叫、子项开始做了不能等叫），`tests/frontdesk-pending-client.test.ts`（批准的待确认记录按结账单认、回到「收银申请」页）。

## 7. Codex 复审修正（e7132c4）

- **盲点的错误也不漏应有**：交班先核对「提交了实点没有、实点与提交的一致吗」，再核对应有现金、应有港元（`SHIFT_CHANGED` 的 details 带着应有的数，没提交实点的不能先看到）。
- **写接口的回复同样过滤**：开班、加入钱箱、离开钱箱、提交实点、交班的回复都过一遍盲点过滤（与查询接口同一个 `blindView`），没提交实点的当班的人拿不到金额。
- **小票机交班表列港元**：打到小票机的交班表（`buildShiftSlip`）与浏览器打印的一样，现金一节列「− 收港元折的人民币（港元另点）」，交班后列应有港元、实点港元与港元长短款，数加得起来。
- **杯贴不把加料算成一杯**：进了水吧出品单的加料（`bill_lines.addon_of`，前台点单与桌台点单都这样记）不单独出杯贴，写进它那杯饮品的杯贴（「加珍珠」，几杯一共加了几份能平分的写每杯几份）；杯数只按饮品本身算。
- 用例：`tests/shift-drawers.test.ts`（盲点下开班、加入、离开的回复不给金额，拿错的应有现金试交班只报要先提交实点、不带应有现金，经理照看），`tests/shift-slip-hkd.test.ts`（小票机交班表的港元几行），`tests/dining-v8230.test.ts`（加料写进饮品的杯贴、两条点单路）。

## 8. Codex 复审修正（e383bf9）

- **别的终端提交了实点**：按钱箱交班时另一台终端点了「提交实点」，这一台轮询带回来的实点覆盖页面上填的（输入框随后锁定），交班的实点就是提交的那个，不会因为旧值点不了或 `BLIND_COUNT_MISMATCH`。
- **杯贴认水吧与点单页同一个算法**：没设点单分类的饮品按「水吧」档口、「调酒」分类等默认归到水吧的（`diningSlotOf`），厨房屏的出品单也标成水吧（`outlet` 由服务端按这个算法给）、能打杯贴，杯贴接口按同一个算法挑饮品。
- **退款申请不按申请人的撤销时限拦**：申请模式下退款区只按单子本身的原因拦（已反结账、没有能退的方式、退完了），超过撤销时限照样能提交，提示「批准时只有店主能批」；批准时开退款单照旧按批准人核对时限（值班经理批超时限的单子 `REFUND_WINDOW`、申请留着，店主能批）。`refund-options` 的 `blocked.code` 本来就分得出时限（`REFUND_WINDOW`）与单子本身的原因。
- 用例：`tests/dining-v8230.test.ts`（按「水吧」档口默认归水吧的柠檬茶：厨房屏标水吧、杯贴只打它），`tests/cashier-v8230.test.ts`（超时限的单子能申请，值班经理批被拒、店主批成）。

## 9. Codex 安全复审修正（8cf7faa）

- **怎么退由批准人定**：退款申请只存「退什么、按什么方式退多少」，每种方式的执行细节（原路退回 `viaTerminal`、商户后台的退款单号 `ref`）与钱箱一样丢掉不存（不然收银员可以把扫码收的钱写成「已在商户后台退了」、填个假单号，批准就记一张完成的退款单，钱不经支付方，经理看不到）。
- **批准时填**：「收银申请」页的批准卡片列出每种非现金方式：这张单扫码收过的微信、支付宝默认勾「原路退回」（系统去支付方退），不勾的、银行卡、其他要登记退款单号或写明怎么退的（至少 2 个字，与直接开退款单同一套核对），填好才能批。接口 `payments: [{ method, viaTerminal?, ref? }]`；不带时扫码收过的微信、支付宝按原路退回（只看「这种方式扫码收过」，重提时算出来的一样），其余要单号。执行细节进开退款单的请求摘要：同一编号同样的细节重提返回同一张，改了 `IDEMPOTENCY_CONFLICT`。
- 用例：`tests/cashier-v8230.test.ts`（申请人带的原路退回、单号不存；不填单号、单号太短拒绝且申请留着；批准人选原路退回照选的走；登记的单号记进退款单；同样细节重提同一张、改了冲突；扫码收过的单默认原路退回、写了待退的支付方退款）。
